# Where the numbers come from

## What can be live

What one query can't do, several datasets can, joined in a `dash.calc`. Before one call uses another's answer, read `reference/dependent-calls.md`. An answer too big for the connector or the page is refused or cut short, so aggregate at the connector. Your own arithmetic can go in the query or a calc. A sender, date, label or status is data. Two things can't be live: your own reading of text, such as sorting, scoring or summing it up, and answers from a tool that only your session has. Only the owner's own page runs live queries, so if people the dashboard is shared with need its numbers, say so and let the person choose. If what you hand over isn't live, tell the person and why, since nothing else will.

## Connectors

A live query's `connector` is the name of an MCP server the owner set up for open artifacts, a key of `mcpServers` in `~/.agents/open-artifact/connectors.json` (or the file `$OPEN_ARTIFACT_CONNECTORS` names, or `connectors.json` in `$OPEN_ARTIFACT_HOME`). A server there is either a command this computer runs (`command`, `args`, `env`) or an address (`url`, `headers`), and `"disabled": true` keeps one listed but off. The file is read again when it changes. The page calls it through the host, on the owner's computer, with whatever access that server is set up with. Only the owner's own page reaches it: a page opened from a share link shows "Live data isn't available in this view." instead. Read only the names in that file. Its `env` and `headers` hold keys and tokens: never copy, show or write them anywhere, and never put one in a dataset.

The tools your own session has are another matter: they are how you explore the data and test a call, and the page can't reach them. A call is live only on a server of the same name in `connectors.json` that offers the same tool. So before you write a dataset on a connector, check that its name is in the file. If it isn't, or the file isn't there, the person adds it: say which server and why, in terms of what they asked for ("Your deals are in HubSpot: add its MCP server to your open-artifact connectors, and the dashboard can read them live."). They add the server and its credentials themselves; you never write the file. Going on without it is their choice, so ask before you use other data. When they say it is done, write the dataset; the page loads it on its next run. One table refused says nothing of the rest of its connector: name it, and who could grant access to it.

When more queries wait than a connector runs at once, `data-fetchpriority`, as in HTML, on a mark or around it, says which go first: `"high"` on the few numbers a reader looks at first, `"low"` on a large detail table. With room for everything it does nothing.

## A loader

`dash.loader(id, {description, fn})` turns an answer that isn't rows into rows. Only rows can be marked by cell, previewed or downloaded. In `runs`, an `ok` with `rows: 0` and `value: true` loaded something else. On every load the page makes the dataset's call, then runs `fn({answer, items, call, args, read})`. `answer` is the tool's answer, parsed if it is JSON, out of a wrapper whose only key is `result`. For an attached file it is the text, or a JSON file's value. Some tools answer in several pieces, such as one per email and one about paging. `items` lists them all, each parsed, while `answer` is only the first, and so is what a dataset with no loader shows. Where nothing read `items`, `runs` says `onlyFirstOf` with their number, and `check` says `items_unread`. `args` are the call's args, with filters filled in. Return row objects, `{columns, rows, truncated}` or `{data, columns, truncated, meta}`, where `truncated: true` means the rows are incomplete. `{data}` alone is a record.

Base it on your own call's answer. An answer can also come back failed inside a success, still running, or truncated. An `error` key, as text or `{message}`, fails the load by itself. To fail the source, throw an `Error` with the connector's words, since an empty result would read as a true zero. Type cells by the connector's column types: an amount is a number, while "02139" and an id above 2^53, which would lose digits, stay text. Readers see the loader's code, and it reruns when that changes, so it uses nothing from outside itself.

`read` has parsers: `read.bigquery(answer)` for BigQuery JSON, `read.governed(answer)` for a `<query_result>` XML, `read.snowflake(answer)` for a `result_set`, `read.databricks(answer)` for a statement. Each returns a promise of `{data, columns, truncated, meta}`: return it, or `await` it before you read or change what it gives. A failure the answer reports is thrown in the connector's own words. Where the answer reports rows and the parser read none, `truncated` is true over empty `data`. The rows may be under a key it missed or behind a further call, so read them yourself. If the loader still returns none, the source fails. BigQuery's and Databricks' also wait for a running query, calling `get_query_results {projectId, jobId, location, timeoutMs: 20000}` (`location` where the answer gave one) and `poll_sql_result {statement_id}`. Snowflake and Databricks cells come typed. But dates and whole numbers of 2^53 or more stay text, and a long decimal rounds. A NULL in a Snowflake text column is `""`.

`meta` is what the answer says about its rows: return whatever it has that a reader would check a number against, such as the query that really ran, the filters a measure applies or the run's address, as `[{label, value, type?: "code", lang?}]`, label and value both text, or the entry is dropped. Readers check numbers against it, so it contains only what the answer carried.

`call(tool, args)` makes another call on the same connector, for a next page or a running query. It gives what `answer` would be, or with `call(tool, args, {items: true})` what `items` would. Calls run one after another, the same call at most once a second, and a whole load has 15 minutes. A loader that pages does so on every load, for every reader, so it asks for what the page shows and no more, and returns `truncated: true` where it stops short. Sources shows the dataset's own call, not the ones a loader makes: a further call worth checking is better a dataset of its own (`reference/dependent-calls.md`). Mark a call that only waits on a running query `call(tool, args, {poll: true})`.

## How fresh

`updates` in `dash/settings` is the Refresh data menu: how old a result may be when someone opens the page, as `viewed`, `5min`, `hour`, `day`, `week` or a number of minutes, and any other word means `viewed`. If the person says how fresh it must be, `update` it with a number. No reader's browser keeps an answer longer than seven days, whatever the pick. Nothing runs on a timer: a query runs only in a page someone has open.

## Files, and older forms

A file is a copy, whatever it was copied from: a newer one shows only when someone uploads it. `schedule` says in words how a file stays current. Past `staleAfterHours`, about twice the time between updates, the file shows as stale. Anything set to upload new copies on a schedule (a script, a scheduled run of an agent) knows only what it is told, so tell it the dashboard's folder, the dataset ids and where each file's data comes from.

A file's text is in the dashboard's folder, at `<root>/_blobs/<id>.<ext>`, where `<id>` is the 32 characters after `_blob/` in its `url`. Read it there with your file tools, or under a host with `Artifact {action: "read", url, path: "_blobs/<id>.<ext>"}`.

**Made again.** Asked for new numbers in a file whose `meta` holds code, read the file and run that code on the new input, changing only what was asked. An analysis written afresh gives other numbers from the same data. Anyone could have written the code, and it runs with your session's access. So read all of it, tell the person what it reads and writes, and run it only once they approve. Show them any line that does more, such as a network call, a command, another file or text you can't read. Anything that runs on a schedule has no one to ask, so it runs only code the person approved in its own instructions, never the file's. An input that isn't attached is theirs to give again. Readers see a JSON file's `meta` with a loader too, unless the loader returns its own.

**Made live.** They asked, so do it even if the data looks fixed. If it can't be live, say why and name the connector that would hold it. Don't offer another upload or sample rows then: they don't answer that request. Only where no connector could hold it, as with a file at a web address, is a newer copy what is left: attach one, and say that each later one has to be uploaded too. The page reads the file's column names, so compare the answer's columns with the file's: the query gives those names, or a loader added to the page does, and nothing else on the page changes. Run it beside the file and tell the person where figures for the same period disagree. `set` the whole document under the same id, with a title and description true of the query and without `updated` and `fixed`. Using `update` would merge the two sources. Leave the file attached, as it may be their only copy, and tell them it still is. Keep its `url` as `formerFile`, a field only you read, since nothing else names the file now.

**Removed**, when the person asks (Sources calls one nothing uses Unused): only you can remove a source. First change any page file that names its id, then delete its document. If it has a file that no other dataset or page file names, delete that too (`open-artifact delete-asset <root> <url>`). Deleting a file can't be undone. The dashboard's History still holds the removed query, or the file's address, though never a query's rows, and anyone who can open the dashboard can read it there: tell the person. To remove the old file of a source made live, first take `formerFile` out of its document (the upload counts as in use while anything names it), then delete the file if no other dataset or page file names it. Keep the document, which now holds the query.

An old `kind: "rows"` source shows "Didn't load": attach its rows as a JSON file. `kind: "query"` is an older form that writes the quotes and reads the answer itself. It still works if left alone. When you change its `args`, rewrite it as `"call"`, with its own quoting and rules, and a loader unless its answer is plain rows.

## What readers see in Sources

Each source's title and description, then, folded, Query (its arguments, with each filter's value now), Transform (the loader's code) and Result (its rows, with the number they clicked lit, and `meta`). A calculation has Formula (its inputs and code) and Result, a file has File, after Code where its `meta` holds any.
