## Publishable text

### Eligibility

- Halden Hack is open to anyone who is **18 or older on the first day of the event**.
- It is **not a student event**. Students, professionals and anyone else may enter.
- Organizers, volunteers, judges, sponsors, or anyone in any other privileged position at the event should not participate as a hacker.
- You must attend in person in Oslo. All team members should actively participate in the event.

### Hacking window

Hacking starts at ⟦START: day, date, time⟧ and ends at ⟦END: day, date, time⟧, Oslo time (Europe/Oslo). That is 48 hours.

### Teams

- Teams can be ⟦1–4⟧ people. Solo entries ⟦are / are not⟧ allowed.
- You may not submit multiple projects.
- You may submit to multiple challenge tracks. A challenge track is a thematic category your project enters. It is not a session stream.
- You may ⟦not⟧ crosspost to other hackathons.

### Work during the event

- You may not work on your project before the event. You must stop development when submissions are due.
- Do not reuse code from previous projects.
- Teams can use an idea they had before the event.
- Teams can work on ideas that have already been done. Hacks do not have to be "innovative".
- Teams can work on an idea they have worked on before, as long as they do not reuse code or other project materials.
- Teams can use libraries, frameworks, or open-source code in their projects. Working on a project before the event and open-sourcing it for the sole purpose of using the code during the event is against the spirit of the rules and is not allowed.
- Teams must stop hacking once the time is up. They may debug and make small fixes to their programs afterward. Large changes or new features are not allowed.

### Submission and public code

- Your code must be available publicly (ideally in a git repository). Remove any API keys before sharing.
- Your code must remain public after the event to be eligible for prizes. If your repository is not public, new winners may be selected.
- You may use publicly available frameworks, but you must list them in a readme.

### AI tools

- Teams may use AI to assist them while coding, such as code completion, code generation, image generation, or similar tools.
- Teams must be honest and transparent about the AI tools they used. List them in your project submission, and answer questions about them when talking to organizers, judges, and other hackers.
- A project should not be a reskin of an existing AI tool.
- Undisclosed AI use is grounds for disqualification.

### Disqualification

Teams can be disqualified at the organizers' discretion. Grounds include breaking these rules, breaking the code of conduct ⟦link to your code of conduct⟧, or other unsporting behaviour. Report concerns to ⟦a person or address you control⟧.

## Ambiguity pass

- **"18 on the first day":** a team member who turns 18 mid-event is out. Say so only if you want that explicit.
- **"Anyone in a privileged position":** this is the MLH wording. A sponsor's employee who is not staffing a booth could argue they are eligible. Decide whether sponsor employees are barred.
- **Age proof:** the text says nothing about it. Checking ID at check-in means collecting personal data. Have whoever owns data protection for the organizing entity review that before you add it.

## 3. The sponsor's IP request

**Do not paste a licence sentence into the rules.** Three reasons:

1. **It is a legal term.** A perpetual, non-exclusive licence on code is a jurisdictional question. It also interacts with the public-code rule above, since the code is already public.
2. **Late additions break the rules.** A rule added after registration or after teams start building applies to a competition nobody entered. Counsel's text must exist before you publish.
3. **Teams must see it before they pick a track.** It applies to one challenge track only, so the track page has to state it and say the licence applies to nothing else.

**What to do:**

1. Send the sponsor's request to counsel through the `event-sponsor-agreement` route.
2. Ask counsel for the clause and for how it composes with the public-code rule.
3. Hold publication of that sponsor's challenge track page until the clause arrives.
4. Publish the general rules above on schedule if the sponsor track can follow before registration opens.

If you have no counsel available, tell me. The honest alternative is to drop the IP term from the track, not to write it ourselves.
