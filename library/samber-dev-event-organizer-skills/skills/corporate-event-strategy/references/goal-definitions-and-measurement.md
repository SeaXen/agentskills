## The four rungs

### Ecosystem goodwill only

The event exists to be well regarded by developers, and the company claims no funnel number from it. Standing in a community, credibility with practitioners, and the ability to be present without selling are the whole return.

- **What it needs**: nothing built. A registration list and a way to run the event.
- **Whose cooperation**: none beyond the organising team.
- **What it costs that is not instrumentation**: the exposure of holding a line no number defends. Asked to justify the spend, a budget owner has an argument and no evidence.
- **When it is honest**: a first edition where nothing is joined yet, or an event whose positioning explicitly forbids a commercial read. In both cases it is a stated posture with an expiry, not a permanent answer.

### Adoption-first

Deeper or broader use of the product among people who already use it. Existing-customer retention reads on this same axis: a customer who uses more of the product is the same measurement as a customer who renews, approached from a different side.

- **What it needs**: a join between the attendance list and product telemetry that identifies accounts, plus a before-and-after window long enough for usage to move.
- **Whose cooperation**: usually one organisation - whoever owns product data - and one approval.
- **Why it sits below pipeline on effort despite being a slower read**: it needs one function to say yes, where a pipeline goal needs two, and cross-function data work is the expensive part.
- **Known weakness**: a usage change after an event has many plausible causes, and the event is rarely the only one. See Counterfactual honesty below.

### Pipeline-first

New opportunity creation attributed to the event.

- **What it needs**:
  - A join between the attendance list and the systems the sales organisation works from.
  - A rule agreed in advance for what counts as event-attributed.
  - Someone who will run the report on the agreed date.
- **Whose cooperation**: marketing and the sales organisation, which is why its effort sits above adoption.
- **The rule agreed in advance matters more than the join**: an attribution rule chosen after the numbers are visible is a negotiation, not a measurement, and every function will argue for the rule that flatters it.
- **Fastest to read, first to fail**: an opportunity carries a date the marketing organisation already reports on, so the number arrives inside the cycle. That same legibility is what makes a quarter with no opportunities a quarter with nothing to defend the line with.

### Blended adoption-and-pipeline

Both goals, with ecosystem goodwill demoted to a constraint on how the event behaves rather than a third goal to report.

- **What it needs**: both joins, plus a reconciliation owner - one person who resolves the two numbers into one story before either function sees the other's version.
- **Whose cooperation**: both functions, plus the standing attention of whoever reconciles.
- **Why it reads slowest**: the slower of its two reads gates it. Publishing the pipeline number alone while adoption is still settling turns a blend back into a pipeline goal in everyone's memory.
- **Why it is the most durable anyway**: it is the only rung with a second story available when the first one has a bad quarter. That is the whole argument for paying its cost, and it only pays off across editions, never within one.

## Why no efficiency line ranks the four rungs

Six pairs exist across the four goal rungs, and none yields a strict dominance relation:

- Blend against pipeline - blocked, each wins one value axis and loses the other.
- Blend against adoption - blocked, each wins one value axis and loses the other.
- Pipeline against adoption - blocked, each wins one value axis and loses the other.
- Adoption against ecosystem-goodwill only - blocked by effort, the winning rung costs more to instrument.
- Pipeline against ecosystem-goodwill only - blocked by effort, the winning rung costs more to instrument.
- Blend against ecosystem-goodwill only - blocked by effort, the winning rung costs more to instrument.

Two mechanisms cover all six pairs, so an efficiency line built on them has no defensible numerator. The two value axes rank the rungs differently, and a single ratio would quietly pick one mandate on the reader's behalf. That choice belongs to the interview's date and mandate questions, not to this menu.

Neither value axis is rank-identical to inverse effort here, unlike the budget-ownership menu in this skill's other reference file. This is therefore a refusal to pick a numerator, not a cheapest-first collapse. An efficiency line scoped to one value axis at a time remains drawable and is not yet drawn.

## The buyer-and-user question

Ask it before any goal that ends in a revenue number.

**Separated.** The developer in the room evaluates, adopts and advocates; somebody else signs. Any join built between attendance and an opportunity records two different people, so what it measures is influence. Report it as influence. A team that reports influence as attribution will be caught by the first person who checks a single record, and the cost is not the correction: it is that every other number in the brief stops being believed.

**Collapsed.** The developer buys, self-serve, with their own or a small team's budget. Attendance and purchase are the same person's two actions, and a pipeline goal reads cleanly.

This is the closest thing in this skill to a genuine business-to-business versus business-to-consumer distinction, and it is not the same split. A business-to-consumer developer product can have a separated buyer (a manager expensing it); a business-to-business product sold bottom-up can have a collapsed one. Ask about this product, not about the category.

Everything else in this skill works identically in both cases. Only the honesty of a pipeline claim changes.

## The four-field measurement commitment

Every chosen goal carries four fields, written before registration opens:

1. **The metric** - one named number, not a category. _Opportunities created_ is a category; _opportunities created within the agreed window, attributed by the rule below, on accounts with at least one attendee_ is a metric.
2. **The owner** - a named person inside the function that will report it. Not the event team, unless the event team is also the function that holds the source system.
3. **The source system** - where the number will be read from, named. If the answer is a spreadsheet somebody will assemble, the join does not exist yet, and the goal that depends on it is not yet available.
4. **The read date** - a date, chosen against the funding cycle rather than against convenience. If the read date falls after the decision the number is meant to inform, the goal cannot defend its own line.

A goal missing any one of the four is a stated intention. This is the skill's only pass threshold, and it is binary and checkable, which is why it carries the weight a numeric bar cannot.

### Positive example

Goal: adoption-first, at a company-run developer day for existing users.

- Metric: share of attending accounts that activate at least one product capability they had not used before, measured in the window between the event and the next quarter's close, against the same share for a matched set of non-attending accounts.
- Owner: named individual in the product organisation who already reports on capability activation.
- Source system: the product telemetry that already identifies accounts.
- Read date: the week after the quarter closes, ahead of the annual planning cycle where the line is renewed.

What makes it pass:

- The number exists in a system that already produces it.
- A named person already reports it.
- The comparison set is decided in advance rather than chosen afterwards.
- The date lands before the decision it feeds.

### Negative example

Goal: _drive pipeline and build community._

- Metric: pipeline, and community.
- Owner: the events team.
- Source system: to be confirmed with sales.
- Read date: after the event.

Every field fails, and the failures compound:

- **Metric** - _Pipeline_ names no rule, so whoever produces the number chooses it; _Community_ names nothing at all, so it will be reported as attendance.
- **Owner** - the events team does not hold either source system, so it will ask two functions for numbers they were never asked to produce.
- **Source system** - _To be confirmed_ means the join does not exist, which means the pipeline goal was never available.
- **Read date** - _After the event_ means the read date will be whenever somebody remembers, which is reliably after the planning cycle that renews the line.

The correct response to this brief is not to improve the wording. It is to go back to the goal menu with Q5's real answer - no join exists - and pick the rung that answer supports.

## Counterfactual honesty

Whether any part of the outcome would have happened without the event is frequently unknowable at the scale a single event operates on. A matched non-attending comparison set is the strongest available answer and is still not proof.

Say plainly in the deliverable which of these applies:

- A comparison set exists and was used.
- A comparison set was not available, so the number is a before-and-after read and the event is one of several plausible causes.
- The outcome is influence rather than attribution, because buyer and user are separated.

Stating which one applies costs nothing and is the difference between a number a funder can defend and a number a funder gets caught holding.
