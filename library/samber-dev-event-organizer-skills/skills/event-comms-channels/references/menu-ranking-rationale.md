# Menu ranking rationale

Contents: why Menu 1's two `==` ties hold · why Menu 2's efficiency line rests on writer-operability rather than a dominance check · why Menu 3's message-bank-over-owner dominance holds · why Menu 4's efficiency line rests on argued ratios rather than a dominance check.

Every ordering on all four menus is this skill's own construction, not a measured ranking. What follows is the argument behind each, so challenge the argument rather than the order.

## Menu 1 - Channel roster

Both `==` ties are argued, not assumed:

- **Chat and event app tie on reach** because each reaches exactly the subset of registrants who opted in a second time, and nothing published anywhere says which subset is larger.
- **Chat and event app tie on speed** because both push to a device already in the attendee's hand within seconds. Their difference is who opted in, which the reach axis already carries.

This menu is clean by care, not by construction: it has genuinely mixed pairs. The list beats chat on reach and loses to it on speed. Chat beats the status page on both value axes but costs more effort, so neither dominates.

One strict-dominance relation exists and is honoured: chat over the app (equal on both value axes, cheaper). This is why the app can never be ranked above chat on efficiency.

## Menu 2 - Message-class routing

This menu is clean by construction, and by-construction is never a pass: no pair of rungs dominates another, because reach tracks effort exactly. No rung buys more value for less effort, so nothing can dominate anything.

The writer-operability axis is this skill's own construction, and it is the whole reason this menu ranks as it does: a routing policy nobody can execute routes nothing. One channel is unambiguous by construction: there is one place. Per-segment channels are the worst of both, because segment membership is a fresh judgement call on every message (does a Wednesday-workshop notice concern "workshop registrants" or everyone?), and the writer resolves it by cross-posting, which rebuilds the noise the segments were meant to remove.

Writer-operability reverses the reach order for three rungs, but it cannot repair a vacuous dominance check: the matrix beats per-segment channels on both value axes and still fails to dominate, on effort alone. The efficiency line rests on the per-rung ratio argued at each bullet, never on a passed dominance check, so challenge that ratio directly rather than the check.

## Menu 3 - Multi-writer consistency

One strict-dominance relation exists and is honoured: the message bank beats a named owner on both value axes at lower effort, so it can never rank below the owner on efficiency.

The first value axis is deliberately scoped to the messages that actually go out during the event, mostly the predictable classes. That scoping is why a frozen template beats a human who drifts, and why widening that quantity to "every message ever written" would reverse those two rungs. State which quantity you mean before reordering anything here.

## Menu 4 - Wind-down after the event

This menu is clean by construction, and by-construction is never a pass. Reachability and non-liability oppose each other on five of the six pairs. The sixth is settled by effort alone, because hand-off beats leave-open on both value axes and still fails to dominate, costing the most effort on the menu.

No pair dominates, so the dominance check finds nothing. The efficiency line rests on the ratio argued per rung, and on Q7, never on that vacuous check.
