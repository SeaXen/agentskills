# Install story for `lark` skill

## Diagnosis

The three issues share one cause. Brew and apt upgrade the binary, and the skill stays where it was installed. Nothing links the two versions, and the skill has no way to notice a mismatch.

Your README commands make this worse:

- `npx skills add larkspur/lark` has no ref, so it follows the default branch. Users get unreleased skill text, or a snapshot that goes stale at install time.
- `gh skill install larkspur/lark lark` resolves the latest tagged release, then HEAD. A pinned skill is then skipped by `gh skill update`.
- Brew and apt users get the binary only, so the skill is a second manual step they do once and never repeat.

I assumed the 1.8.0 tag shipped with a skill that still says `lark push`. If HEAD already has the 1.8 syntax, the three reporters hold old installs and the content fix is smaller, but the channel fix is the same.

## Lockstep audit

| Rule | Status |
| --- | --- |
| 1. Skill lives in the code repo | ✅ `skills/lark/SKILL.md` |
| 2. `metadata.version` equals the code version | ❌ Unknown, likely absent or stale |
| 3. Every tag carries a matching skill | ❌ The 1.8.0 tag carries a stale skill |
| 4. A stale skill fails the release before the tag exists | ❌ No gate |
| 5. Renames count as breaking | ✅ Keep the name `lark` |

## Plan, in order

### 1. Fix the content (about 1 hour)

1. Open `skills/lark/SKILL.md` with the two-sided version guard from the skill. The body line `Skill version: X.Y.Z` sits outside any code fence.
   - Run `lark --version` first.
   - Same major.minor: continue.
   - Major or minor differs, in either direction: trust `lark --help` over the skill's command names, and tell the user to reinstall from their version's tag.
   - A `dev` build: continue.
2. Rewrite the push section to the 1.8 syntax. Defer flags and arguments to `lark push --help`. The skill covers when to use push and the pitfalls.
3. Use the old-syntax failure as the first explicit pitfall, with the correct 1.8 command beside it. Say which of these is true, because I don't know:
   - `lark push` was renamed.
   - Its flags changed.
   - It was removed.
4. Set `compatibility: Requires the lark CLI on PATH.` with no version number. Set `license` to the repo's license.

### 2. Cut 1.8.1 (about 1 hour)

- The 1.8.0 tag is immutable and ships a stale skill. Release the fix as 1.8.1, with `metadata.version: "1.8.1"` and `Skill version: 1.8.1`.
- Write the release notes as the pinned install block, with the tag generated by the release job:

```
Agent skill for this release:
  gh skill install larkspur/lark lark@v1.8.1
  npx skills add larkspur/lark#v1.8.1
Already installed? Re-run with the new tag.
```

- Add `skills/**` to goreleaser `archives.files`, so tarball users get it too.

### 3. Fix the README (15 minutes)

Replace both commands with tag-pinned ones that use a placeholder:

```
lark --version            # prints e.g. 1.8.1
gh skill install larkspur/lark lark@v<version>
npx skills add larkspur/lark#v<version>
```

The README then never goes stale, and it is the listing driver for skills.sh.

### 4. Answer the three open issues

- Reply with the pinned reinstall command.
- Say plainly that skills installed before 1.8.1 carry no guard. Reinstalling is the only fix for them.

### 5. Add the release gates (about half a day)

Assuming goreleaser with plain tags, since a Go CLI on brew, apt and tarball almost always means that:

- **Version bump:** a `make release VERSION=x.y.z` target runs `scripts/check-skill-version.py x.y.z --write --skills-dir skills`, then the gates, then commits, tags and pushes. Goreleaser runs after the tag and cannot bump. Copy the script from the skill into your repo.
- **Gate 2, version equality:** run on pull requests against `git describe --tags --abbrev=0`, in `make release` before tagging, and on the tag as a backstop.
- **Gate 3, content check:** build the snapshot binary with `goreleaser build --snapshot --clean --single-target`. Extract every `lark …` invocation from the skill's code blocks and run `lark <subcommand> --help`. Assert every flag appears in the output, and capture stderr too. This is the check that would have caught `lark push`.
- **Gate 1, spec validation:** a one-line frontmatter check.
- **Gate 4, changed-surface check:** fail a pull request that changes the CLI help tree without touching `skills/`, unless it carries a `skill-unaffected` label.
- **Gate 6, security scan:** Snyk Agent Scan over `./skills`, using the workflow snippet in the skill's CI reference. It needs a `SNYK_TOKEN` secret and skips fork pull requests.
- **Deferred:** gate 5 (golden agent tasks). Promote it after the next skill-caused issue.

Run gates 1-3 and 6 before tagging, and gates 1-4 and 6 on pull requests.

### 6. Bundled install (the real fix)

Almost everyone installs through brew or apt, and stale-skill issues are already arriving. Both are the skill's stated promotion conditions for bundling the skill with the binary. A tag-pinned git install is only correct at install time, so a brew upgrade breaks it again.

1. Embed `skills/lark/` with `//go:embed` from the module root.
2. Add `lark skills install`, which writes or syncs the skill into the agent's skills directory.
3. Record the synced version in a small state file.
4. On each run, compare the recorded skill version with the binary's version. On a mismatch, print one line an agent can act on: `skill lark 1.8.0 differs from lark 1.8.1; run: lark skills install`.
5. Skip the notice in CI and for `dev` builds, and add an env var to silence it.
6. Version match is then guaranteed by construction. Rules 2 and 3 are enforced by the embed, with gate 2 as the backstop.

You'd keep the git-based commands as the fallback for users who don't want the subcommand. Effort is about 1-2 days for the embed, the subcommand and the drift notice. Brew and apt users still need one `lark skills install`, so two nudges are worth adding:

- **Interim (about 10 minutes, do it in step 2):** print the pinned install command in the footer of `lark --help`.
- **After the subcommand ships:** add goreleaser `brews[].caveats`, which prints on brew install and upgrade, saying `lark skills install`. Check the field name against the current goreleaser docs before relying on it. For apt, a postinst message is less visible, so rely on the drift notice there.

### 7. Skip for now

- Plugin manifests (Claude, Codex, Cursor, Gemini) and a marketplace. Each one adds a version field to keep in sync. Add them when users ask, not before.
- ClawHub and OpenClaw gating.
- Directory submissions. The README and tag-pinned commands drive the skills.sh listing.

## Done when

- A release with a deliberately stale `metadata.version` fails before its tag exists.
- A release whose skill names a removed flag or command fails CI.
- Every release note prints a tag-pinned install command.
- A brew upgrade followed by an agent run prints a drift line if the skill is stale.
- No new "agent used old syntax" issue appears after 1.8.1 and the first skills sync.
