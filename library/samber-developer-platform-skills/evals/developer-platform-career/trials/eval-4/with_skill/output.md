## What actually gets you hired

Your gap is that you have no developer-facing product on your CV. Close it in this order.

1. **Treat your internal tooling as a practice ground.** Find the part of your internal tooling that other teams or systems consume through an API or integration. Own its contract, versioning, deprecation notices and docs.
   - ⚠️ This is a **hypothesis**. I found no named practitioner who made this exact transition. It is plausible because internal APIs carry less external accountability, so it is a lower-stakes place to practice.
2. **Write 2-3 sanitized design docs from that work.** Cover a breaking-change decision, an integration-friction fix and a roadmap call. Remove confidential detail. The skill flags real employer design docs as the hardest portfolio artefact to publish, so sanitize early.
3. **Write one public API critique.** Pick a public API and review it against Google's AIPs, Zalando's guidelines and Microsoft's REST guidelines. This costs nothing and shows the judgment the track is screened on.
4. **Prepare for the API-design interview.** Meta now runs API design as a separate round from system design. A common practice prompt is a card-payments API where the users are the integrating developers.
   - For PMs, the bar is how you scope, structure and communicate the design. It is not implementation depth.
   - Some PM loops (Uber) add a technical conversation with an engineer, so you must explain APIs without hand-waving.
5. **Build an open-source trail if time allows.** Docs fixes, SDK issues or API-spec contributions all count.
