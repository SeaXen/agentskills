# Ashgrove Robotics SDK launch plan: publishing and iOS consumption

I haven't run any of this. It comes from my knowledge of Kotlin Multiplatform, the vanniktech plugin and the Plugin Portal. Items marked "verify" are ones I'm less sure of.

## 1. Don't split Maven Central publishing across two runners

**Do this first: ❌ the two-runner split, as planned, will produce a broken release.**

- A KMP release is one Gradle module with a root publication (`robotics-sdk`) plus per-target artifacts (`-jvm`, `-android`, `-js`, `-iosarm64`, `-iossimulatorarm64`).
- The root publication carries the Gradle module metadata that maps every target variant. It is generated by the host that publishes it.
- An ubuntu host can't build the Apple targets, so its root metadata is incomplete. Gradle and Kotlin consumers on iOS targets can then fail to resolve the SDK. Kotlin's docs recommend publishing a multiplatform library from a Mac host for this reason.
- Two `publishAndReleaseToMavenCentral` runs create two Central Portal deployments for the same version, and the "AndRelease" part releases each one automatically.
- Central versions are immutable. The second deployment either fails on the duplicate root files, or the first one ships incomplete and can't be fixed. The only recovery is a new version number, five days after launch.

**Fix: one macOS job publishes all SDK targets in one deployment.**

- Run ubuntu on PRs and main for tests (jvm, js, android unit tests). That is where the CI minutes are saved.
- Run macOS only on tag, once.
- On a private repo, macOS minutes bill at 10x. A 15-minute tag run is about 150 billed minutes. That is small next to a bad release. On a public repo it's free.

**Before launch day:**

1. Push a `1.0.0-rc.1` tag through the real pipeline. Use `publishToMavenCentral` (no auto-release) first. In the Portal UI, inspect the deployment and check that the root module's `.module` file lists the iOS variants. Then release it.
2. Confirm the `com.ashgrove` namespace is verified in the Central Portal. This is a DNS TXT record on the company domain and can take a day or more.
3. Put the in-memory GPG key and Portal token in secrets (`ORG_GRADLE_PROJECT_mavenCentralUsername`, `...Password`, `signingInMemoryKey`, `signingInMemoryKeyPassword`). Make sure the public key is on a keyserver.

## 2. Gradle plugin on the Plugin Portal

This is a separate publication and a separate job. It is JVM-only, so it stays on ubuntu.

- **Plugin ID.** `com.github.ashgrove.robotics` doesn't match your Maven group `com.ashgrove`. The `com.github.` prefix also reads as a GitHub-user namespace. Recommended: `com.ashgrove.robotics`. The ID is permanent once published and users hard-code it, so decide before day 1.
- **Publishing.** Use the `com.gradle.plugin-publish` plugin. It needs `gradle.publish.key` and `gradle.publish.secret` from a Portal account, stored as CI secrets. Run `./gradlew publishPlugins`.
- **Approval.** Verify whether a first-time plugin ID needs Gradle review before it is visible. If so, publish an rc now rather than on launch day.
- **Ordering.** Release the SDK first, then the plugin. The plugin's tests should resolve the released SDK version, not a snapshot.
- **Resolution.** Users need `gradlePluginPortal()` in `pluginManagement` repositories. State this in the docs.

## 3. How the iOS team consumes it

**Short answer: they don't consume the Maven artifacts.** Xcode can't resolve Maven Central or the Kotlin klibs. They need a native binary that Swift can import. Ship an XCFramework through Swift Package Manager.

### What you build

1. In the SDK module, declare a framework for the iOS targets and assemble an XCFramework with Kotlin's `XCFramework` Gradle API:

   ```kotlin
   val xcf = XCFramework("RoboticsSDK")
   listOf(iosArm64(), iosSimulatorArm64()).forEach {
       it.binaries.framework {
           baseName = "RoboticsSDK"
           isStatic = true
           xcf.add(this)
       }
   }
   ```

2. Run `assembleRoboticsSDKReleaseXCFramework`, zip the result, and run `swift package compute-checksum` on the zip.
3. Attach the zip to the GitHub Release for the tag.
4. Publish a `Package.swift` with a `.binaryTarget(name:url:checksum:)` pointing at that zip.
5. Use a small dedicated repo, for example `robotics-sdk-swift`. CI bumps `Package.swift` and tags it after the zip is uploaded. In the SDK repo the checksum would only exist after the tag, which is a chicken-and-egg problem.
6. The iOS team then adds the package by URL in Xcode (File > Add Package Dependencies) and writes `import RoboticsSDK`.

This step needs macOS, so it belongs in the same tag job as the Maven publish.

### Decisions to make before launch

- **Intel simulator.** The targets list has no `iosX64`. Apple-silicon Macs are fine. Intel Macs and some CI runners won't run the simulator slice. Add `iosX64` or tell the iOS team.
- **Swift ergonomics.** The default Objective-C export mangles Kotlin APIs:
  - `suspend` functions become completion handlers.
  - `Flow` is not usable as an `AsyncSequence`.
  - Sealed classes and enums lose exhaustiveness.
  - Generics are erased.

  Have the iOS team build a small spike app against the XCFramework now. Then pick one of:
  - SKIE, which generates idiomatic Swift for these.
  - Kotlin's Swift export, which is newer; verify its maturity for your Kotlin version.
  - A hand-written Swift wrapper.

  Don't discover this on launch day.
- **CocoaPods.** Skip it. Verify the CocoaPods trunk read-only date, which I recall as late 2026. SPM is the right path for a new launch.
- **Multiple Kotlin frameworks.** If their app also embeds another Kotlin/Native framework, two static Kotlin runtimes in one binary can conflict. Ask them.
- **Support policy.** Say which Xcode and Swift versions you support.

### What to tell the iOS team

> Add the Swift package `https://github.com/ashgrove/robotics-sdk-swift` at version `1.0.0` in Xcode, then `import RoboticsSDK`. No Kotlin or Gradle is needed. The API is Kotlin-defined, so suspend functions and flows may look different from native Swift until the wrapper decision is made.

## 4. Tag workflow

```yaml
name: release
on:
  push:
    tags: ["v*"]

jobs:
  sdk:                       # one macOS job, one Central deployment, plus the XCFramework
    runs-on: macos-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: 21 }
      - uses: gradle/actions/setup-gradle@v4
      - run: ./gradlew publishAndReleaseToMavenCentral assembleRoboticsSDKReleaseXCFramework --no-configuration-cache
        env:
          ORG_GRADLE_PROJECT_mavenCentralUsername: ${{ secrets.MAVEN_CENTRAL_USERNAME }}
          ORG_GRADLE_PROJECT_mavenCentralPassword: ${{ secrets.MAVEN_CENTRAL_PASSWORD }}
          ORG_GRADLE_PROJECT_signingInMemoryKey: ${{ secrets.SIGNING_KEY }}
          ORG_GRADLE_PROJECT_signingInMemoryKeyPassword: ${{ secrets.SIGNING_KEY_PASSWORD }}
      # zip the XCFramework, compute the checksum, upload to the GitHub Release,
      # then bump Package.swift in robotics-sdk-swift and tag it

  plugin:                    # separate, cheap, ubuntu
    runs-on: ubuntu-latest
    needs: sdk
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: 21 }
      - uses: gradle/actions/setup-gradle@v4
      - run: ./gradlew :plugin:publishPlugins
        env:
          GRADLE_PUBLISH_KEY: ${{ secrets.GRADLE_PUBLISH_KEY }}
          GRADLE_PUBLISH_SECRET: ${{ secrets.GRADLE_PUBLISH_SECRET }}
```

PR workflow: ubuntu `./gradlew check` for jvm, js and android. Add a macOS `iosSimulatorArm64Test` only on main or nightly if you want to limit macOS minutes.

## 5. Five-day schedule

| Day | Action |
|---|---|
| 1 | Verify the Central namespace. Settle the plugin ID. Start the iOS Swift spike. Create the Portal and Plugin Portal secrets. |
| 2 | Rework the pipeline to a single macOS job. Add XCFramework assembly. Set up the Swift package repo. |
| 3 | Run the rc tag with `publishToMavenCentral`. Inspect the root module metadata. Publish the plugin rc. The iOS team consumes the rc through SPM. |
| 4 | Fix the findings. Decide on SKIE or a wrapper. Do a docs pass (Gradle snippet, plugin block, SPM snippet). |
| 5 | Tag `v1.0.0`. Verify resolution from a clean machine for Gradle, the plugin and SPM. |

One caveat on day 3: an rc published to Central stays there permanently. Use a clearly pre-release version string.
