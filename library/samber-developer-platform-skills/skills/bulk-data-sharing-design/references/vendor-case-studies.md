## Sharing-platform landscape (the substrate options for the native-share camp)

- **Snowflake Secure Data Sharing** - cross-cloud, cross-region, role-based; a "reader account" lets a recipient without a Snowflake license still query. Consumers pay only query compute; shared data adds zero consumer-side storage because nothing is copied. Strongest when consumers are SQL-first analysts. (Snowflake's comparison-page claims about competitors are vendor marketing.)
- **Databricks Delta Sharing** - open REST protocol, not a Databricks-only feature: any open-source client (pandas, Spark, Rust, Python) reads a share without deploying Databricks. Governance via Unity Catalog. Cost caveat (raised by a competitor source - weight accordingly): consumer reads from a remote region can incur egress the _provider_ pays, scaling with consumer query volume. Adoption figures are vendor-reported:
  - 300%+ year-on-year usage growth, two years running.
  - 16,000+ recipients.
  - 40% of shares go to recipients outside the Databricks ecosystem.
- **BigQuery sharing / Analytics Hub** - subscribers get an opaque, read-only linked dataset inside their own project and VPC perimeter; a "restricted export" option blocks re-exporting shared data out of that perimeter entirely. Authorized views exclude specific columns (the PII-exclusion tool). Strength is GCP-native integration rather than cross-cloud reach.
- **Iceberg REST Catalog** - the vendor-neutral option: an OpenAPI-specified metadata protocol now the de facto standard in the Iceberg ecosystem; any compliant client (Snowflake, Trino, Flink, Spark, PyIceberg) reads from any compliant catalog (Polaris, Nessie, Unity Catalog, Gravitino), with credential vending and OAuth2 client-credentials auth. Caveat: the spec is intentionally silent on performance, and two compliant catalogs can differ by orders of magnitude in response time. Delta Sharing added first-class Iceberg support (2026-01), so the two open options are converging.
- **Salesforce Data Cloud Zero Copy** - metadata layer plus query pushdown (compute runs where the data lives); GA with Snowflake and BigQuery since 2024-04-25, bidirectional, converging on Iceberg at the storage layer via File Federation (Beta).
- **AWS Data Exchange** - the marketplace-flavored option: vends a named bucket-style alias per S3 data asset and mints a separate KMS grant per subscriber, so each recipient decrypts only their own entitled data.

One practitioner data point on the "does the recipient need my platform?" fork (LinkedIn PoC writeup - anecdote, not benchmark): Delta Sharing could share directly to a recipient by email, while equivalent Snowflake performance required data in Snowflake-managed storage and accounts on both ends.

## Delta Sharing protocol mechanics (the reusable design pattern)

- The sharing server **never proxies bytes**. The recipient's client authenticates, queries a table, and receives a short-lived pre-signed URL pointing directly at the Parquet file in object storage. The recipient pulls from storage; throughput scales with the storage layer, and the server's job shrinks to authorization plus URL-signing. This is the pattern to copy whatever mechanism you build.
- Access is time-bound by token expiry (30 days is a common real-world setting), not per-request ACL checks - pin your access-review cadence to that TTL.
- Built on Delta Lake's transaction log (`_delta_log/`), which is what gives shares table versioning and time-travel for free, versus a flat pile of Parquet files with no change history.
- Multi-tenant mapping for SaaS: one table partitioned on `tenant_id`, sharing only the partitions belonging to each recipient - every tenant's share backed by the same physical table, no per-tenant copies.
- Two-tier access in practice: bulk temporary cloud credentials when the asset qualifies, per-file signed URLs as the safe default.

## Build vs partner: the evidence

The practitioner consensus: **buy or partner for standard delivery paths; build only for what no vendor covers.**

- The anchor: Fivetran - whose entire business is data movement, and which had a working reverse-ETL prototype - acquired Census (announced 2025-05-01) instead of shipping its own. CEO George Fraser: it "would be a better use of resources to bring on a company that had already figured it out," because "if you look at the code underneath [these] services, they're actually pretty different" - read-path and write-path movement don't share expertise.
- Fivetran's stated reason write paths are harder: "Read APIs on most SaaS tools tend to be relatively straightforward, whereas write APIs are much more complex (e.g., each tool handles deletes differently)."
- The scale of the maintenance burden being avoided (Airbyte co-founder Michel Tricot): "we built and scaled over 1,000 data ingestion connectors to replicate 100TB worth of data every day."
- The named cost risks of buying: usage pricing that starts affordable and scales badly ("credit spending explosion"), and the "double vendor premium" - paying separately for extraction compute and warehouse compute when a warehouse-native path pays once.
- Revisit trigger (self-set, not a published figure): vendor usage pricing crossing the fully-loaded cost of roughly 1-2 dedicated data engineers, or governance/residency requirements no vendor meets.

For a SaaS vendor designing a bulk surface, "partner" usually means: use the destination warehouse's own sharing primitive (as Stripe did with Snowflake) rather than rebuilding file transfer, and let established movement vendors carry the long tail of destinations.
