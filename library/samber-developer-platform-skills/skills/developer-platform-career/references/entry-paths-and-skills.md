# Entry paths and skills

Contents: requirements and prerequisites, hard/soft skills per level, training path from zero - several sub-questions came back thin and are flagged as such rather than filled with invented detail.

## Requirements and prerequisites

No dedicated academic degree or bootcamp path exists for "developer platform engineer" or "API product manager" as such. Both are specializations layered onto a general software-engineering or product-management base, confirmed across every sourced job posting.

- **Engineering-side entry bar.** GitLab's Partner Integration Engineer family requires a bachelor's degree or equivalent, proficiency in Ruby/Rails or Go (or willingness to learn), modern SDLC practice (DevSecOps, CI/CD, IaC), and - notably - an **open-source contribution history** as a named requirement even at the associate level. Stripe's Staff Software Engineer, API Platform posting sets a much higher bar: 12+ years of technical experience and 5+ years specifically in strategic technical leadership, with explicit prior experience "leading engineering team(s) working on API design, abstractions, frameworks, or client libraries."
- **API design portfolio expectations.** Multiple current backend-engineering job postings list "designing and building internal & public APIs," "API design and development," and "author and review technical design documents, RFCs, and root cause analyses" as core, named responsibilities rather than nice-to-haves. RFC-writing and API-design-decision documentation is a real, checkable artifact category in this field, the way a talk or blog post is for DevRel - but no single named public repository of "API design RFC portfolios" comparable to a GitHub profile exists. The equivalent artifact is a design doc or RFC from a real employer, which is harder to make public than a DevRel blog post.
- **Certifications.** Largely not meaningful. The one real, currently-running credential is apidays' **apiMasters** certification program, positioned as unlocking "new career opportunities" within the API community - but no independent evidence shows employers weight it in hiring decisions. Treat it the same way DevRel treats vendor certifications: informational at best, never a stated hiring gate. A Postman certification program was referenced in passing but its live page could not be confirmed - verify existence and positioning before citing it.

## Hard and soft skills per level

No published, cross-company skills matrix comparable to DevRel's own frameworks exists for API Product Manager or Platform Engineer. What is directly sourced:

- **Staff-level platform engineering** (Stripe posting): hands-on technical leadership spanning "architecture and design, vision, direction, and requirements setting"; ability to communicate from "high-level discussions to detailed coding"; thrives on high autonomy; proficiency in Java, Ruby, Python, or Go.
- **API Product Manager, senior level**: "develop and execute the product strategy and roadmap for API products, aligning with the company's overall business objectives," plus competitive analysis and monetization/pricing model design - the PM-track skill that gains weight with seniority is commercial/ecosystem judgment, not deeper technical depth.
- **Partner/Integration Engineer** (GitLab): the associate-to-full-role jump is an experience threshold on the _same_ responsibilities, not a change in scope; the jump to manager adds team hiring/development, mentorship, and being the subject-matter expert for cross-functional partner relationships.

**Flagged as thin:** a level-by-level hard/soft skill breakdown for the engineering platform track (junior through staff) was not found as a published framework. Only the staff-level bar (via Stripe) and the associate/full/manager framing (via GitLab) are directly sourced. Treat any finer-grained ladder as inferred from general software-engineering ladders, not platform-specific, until better sourcing is found.

## Training path from zero

**Present as a hypothesis, not a verified pattern.** The internal/external API distinction implies a real, lower-stakes practice ground: building internal APIs inside an existing engineering org carries less external-consumer accountability (no public docs, no formal deprecation notice, no external SLA) than shipping a public API. This makes "build internal platform/API experience first, then move to a team that ships externally" a plausible, lower-friction route, but no named practitioner account of this exact transition was found.

What is evidenced instead: GitLab's own ladder (Associate Partner Integration Engineer -> Partner Integration Engineer -> Manager) is a real, named example of formal internal progression once already inside a company with this function - useful as a concrete case, not as a generic industry pattern.

For the PM track, the closest sourced statement is generic career-site framing: "many API Product Managers start in roles such as product analyst, software developer, or project coordinator... transition into mid-level roles like Senior Product Manager" - treat as directional, not authoritative.
