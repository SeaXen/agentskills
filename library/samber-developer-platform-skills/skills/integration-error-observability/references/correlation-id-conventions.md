# Correlation ID Conventions

How to identify a failed call so an external developer can hand your support team one string that locates it exactly.

## Request ID versus correlation ID

Two identifiers, routinely conflated, doing different jobs:

- **Request ID** - identifies exactly one HTTP call and its response. Generated at your edge if the client did not supply one.
- **Correlation ID** - identifies an entire multi-call transaction. One user action can produce a dozen request IDs under a single correlation ID.

Most platforms ship the request ID and stop. The correlation ID is what a partner needs when their failure is "the checkout flow broke" rather than "this call returned 500" - a flow spanning several of your endpoints, where the interesting question is which step failed, not what one call returned.

If you support only one, support the request ID: it is the one that appears in an error the integrator is already holding. Add the correlation ID when the audit shows multi-call flows in the ticket pile.

## Header conventions and platform variants

An opaque per-request correlation header is the de facto convention, generated or forwarded by essentially every gateway, load balancer and cloud edge - but `X-Request-Id` is not the one literal name they converge on. Every major platform brands its own header instead (sourced: AWS, GitHub, Vercel, Twilio docs, see variants below), so treat "an opaque request identifier exists" as the convention and the header's name as a per-platform choice. The value should be an opaque random string - a UUIDv4 is the default choice, because it is collision-safe under load and carries no information, unlike a sequential counter (leaks volume) or a timestamp-derived value (leaks timing and collides under concurrency).

Named variants exist and are citations rather than requirements:

- GitHub returns `X-GitHub-Request-Id` with colon-separated hex segments, e.g. `1C73:26D4:E2E500:1EF78F4:62EC2479` (sourced: GitHub docs).
- Vercel returns `x-vercel-id`, listing the regions a request hit and the region a function executed in, which also lets Vercel detect infinite loops (sourced: Vercel docs). Vercel's own support terms ask users filing a case to include this header's value - a first-party instance of the support-lookup workflow below (sourced: Vercel support terms).
- Cloudflare returns `Cf-Ray`, a hashed value encoding the data center that handled the request, meant to be logged at the origin so a request can be matched between Cloudflare's edge and the origin's own server logs (sourced: Cloudflare docs).
- AWS load balancers return `X-Amzn-Trace-Id` in the form `Root=1-<hex-timestamp>-<hex-id>`, generated by the load balancer when the client didn't supply one (sourced: AWS docs).
- Twilio returns `Twilio-Request-Id` and its own REST API best practices tell developers to check for it before contacting support (sourced: Twilio docs) - the same first-party support-lookup pattern as Vercel's.

Pick one header name, document it, and never change it - integrators write parsers against it.

The standards-track alternative is the W3C `traceparent` header: `version-trace_id-parent_id-trace_flags`, where the trace-flags byte's low bit carries the sampling decision (sourced: W3C Trace Context spec). Choose it when you already emit distributed tracing internally and want external calls to join those traces. Choose the plain request ID when you do not, since `traceparent` without a tracing backend behind it is a more complicated string that resolves to nothing.

Accept a client-supplied ID when one arrives, and echo it rather than overwriting it - an integrator who generates their own correlation ID is trying to join your logs to theirs, which is the behaviour you want.

## Echo and propagation rules

- **Echo in response headers on every response**, not only failures. A call that returned 200 and did the wrong thing is a real ticket class, and it has no error body to carry an ID.
- **Echo in the error body too**, coordinating with `samber/developer-platform-skills@api-error-design`, which owns the payload shape. Header-only means the ID is lost the moment an integrator's client logs the parsed body and discards the response headers - which most do.
- **Never regenerate mid-flight.** If your edge assigns an ID and an internal service assigns another, the string the integrator holds resolves to nothing.
- **Propagate on downstream calls.** When handling the request causes calls to sub-processors, carriers or other providers, forward the same identifier so one lookup surfaces the whole chain.
- **Propagate on retries.** Your own internal retries must carry the original ID. A retry that generates a fresh one splits a single failure into unlinked fragments.
- **Log it on both sides of every boundary** - inbound at your edge, outbound at each downstream call - so the chain reconstructs even when a hop fails.

## The support-lookup workflow

The design target: an integrator resolves their own failure before writing to you, and when they do write, one string is enough. Three things have to be true:

1. The ID is in something the integrator already has (response header, error body, or their own client logs).
2. A surface they can reach resolves it - the developer-facing request log. This is the rung platforms skip, and skipping it converts the ID from a self-service tool into ticket decoration.
3. Your support team resolves the same string against internal logs, including the downstream hops the integrator cannot see.

Document the lookup path in the developer docs, next to the error documentation rather than in a separate observability page: the moment an integrator needs it, they are reading about an error.

Two platforms document this exact workflow, by name, in their own first-party docs rather than leaving it implicit: Plaid's API reference and error docs both instruct developers to "include the `request_id` when contacting support regarding a specific API call," and PayPal's integration checklist and troubleshooting docs name `PayPal-Debug-Id` as the identifier to retain and hand to support (sourced: Plaid docs, PayPal docs). Both name the support-resolution use case explicitly, which is what separates this from generic request tracing.

## A negative example

What a broken implementation looks like from the outside:

```
Integrator: "Call failed at 14:22 UTC, request ID req_8f2c1ab9d3e04c7f."
Support:    "That ID isn't in a system I can search. Can you send the full
             request body, the endpoint, and your account ID?"
```

Everything the ID exists to prevent happens anyway. The usual causes, in order of frequency:

- The ID is generated at the edge for tracing but never persisted alongside the application logs support actually searches.
- Each internal service generates its own, so the returned ID belongs to a hop that has no record of the failure.
- The ID is returned but dropped on the downstream call that actually failed, so the chain ends one hop short of the answer.
- The ID resolves internally, but no external surface exists, so every lookup still costs a support round-trip - the header shipped, the log never did.
