# Developer journey map — SREs at mid-market companies, 2026-09-19

Two things up front, because they gate everything below them.

**Your tracking is not broken.** A 61% direct share on a docs site is the expected outcome for this exact audience, not a red flag. Aggregators, Slack/terminal-pasted links, privacy browsers and AI coding assistants all strip referrers — Demand Curve estimates roughly 70% of AI-assistant-driven traffic arrives with none at all (a newsletter estimate, not a study, but directionally the same mechanism). SREs also skew Linux/Firefox/ad-blocker-heavy, which is precisely the cohort Plausible measured blocking third-party analytics scripts hardest (82.3% on Linux, 88.3% on Firefox, in their August 2021 single-site measurement — the only public figure of its kind, from an interested vendor, so treat it as directional). Put together, your 14,200 is more likely an *undercount* of real reach than a broken or inflated number. A six-week instrumentation project is not the right next step before this is confirmed cheaply — see Gaps for the cost-ordered alternative.

**The 14,200/61% figure can't sit in two rows as a raw count.** It's one measurement from one source, and this skill's evidence rule is explicit: never write an absolute traffic number in a cell, because the same blocking bias that undercounts your total also varies page-to-page, so the number isn't even internally comparable across stages without a breakdown you don't have yet. I've put it once, in Awareness, labeled `inferred`, with the caveats above attached. What you're calling "evaluation" is this model's Onboarding stage — I've noted below what concrete, cheap number would actually belong there instead.

## Scope

- **Segment:** SREs at mid-market companies. One map, one segment, per the skill's own rule — do not reuse this for a platform-team or hobbyist audience later.
- **End state:** production usage.
- **Stage model — deletion pass:** the end state names the terminal stage, and only one published model's terminal stage is "production": the **API and platform five-stage arc** (Awareness → Onboarding → Integration → Production → Advocacy). Revell six-stage ends at standardization, AAARRRP at revenue, Orbit at advocate, the OSS contributor funnel at return, and the unsourced discover→advocate default also tails at advocate — none of those match a production-usage mandate, so all five are off the menu.
- **Rank of the survivor:** the API arc is also this skill's cheapest model to stand up (an hour to a week — first call, integration and production usually already sit in product telemetry) and its most efficient. Both things line up here; that's not always true, but it is this time. Recommended, and used below.
- **Open questions I answered by default, flag if wrong:** (1) whether Cindershell is self-serve, sales-assisted or open source — the interview never reached this, so I've modeled a self-serve/individual-adoption path with any internal approval step folded into Production as friction, per the skill's guidance for that case (see Buyer lane). (2) Exact owning teams for Integration and Production — named generically as "product/platform engineering"; rename to match your org chart. Both are cheap to correct in a re-read; neither changes the stage model.

## Moments

- **First success** — first successful Cindershell command run against a real (non-toy) target. Time-to-first-success: not instrumented yet; needs CLI-side telemetry (see Gaps).
- **Moment of truth** — the decision to wire Cindershell into the team's CI/IaC pipeline rather than run it ad hoc from a laptop. For an infra-mutating CLI, this is where the team stops evaluating and starts depending on it, more than the first local run.
- **Abandonment point** — unknown. Best guess, labeled a hypothesis, not a finding: somewhere in Onboarding, at the point between "ran it once locally" and "trusted it enough to point at something real" — this is the generic high-friction point for infra-mutating CLIs, not something measured for Cindershell specifically. Confirm with 3 abandonment interviews before the next re-read.

## Leak

**Onboarding — nominated provisionally, not measured.** With one aggregate GA number and nothing else instrumented, no stage-to-stage conversion rate can actually be computed yet, for any stage. I'm naming Onboarding anyway because the format requires exactly one leak and because it's the strongest reasoned candidate available: it's fully inside the product team's control (unlike Awareness, which runs mostly on channels nobody here can move directly), it's the structural trust-threshold every SRE hits with an infra-mutating tool, and it's the cheapest stage to both instrument and fix. Treat this as the map's working hypothesis, to be replaced with a real rate — or a different stage entirely — once the Gaps below close. Don't let "the leak is already named" substitute for confirming it.

Why it would leak, if the hypothesis holds (BJ Fogg's B=MAP, applied only after the stage is picked): most likely **ability**, not motivation — an SRE who reached the install docs already wants this to work; what stops them is the step being long, needing an undeclared prerequisite (credentials, a safe target to point at, a rollback story), or an unfamiliar routine. That's a docs/dev-ex fix, not a positioning fix — confirm with a friction log before writing any copy.

## Handoff

- **Owner of the fix:** developer experience / docs (confirm exact team name).
- **Signal to watch:** % of docs sessions reaching the install/quickstart page, replaced with % of installs reaching first successful real-target command once CLI telemetry exists.
- **Re-read date:** 90 days from today (~2026-12-18), or sooner if a launch, pricing change, docs rewrite or new SDK moves a surface first.
- **On the agency's proposal:** don't commission it as scoped. Recommended order instead, cheapest first: (1) pull the existing GA property's page-level breakdown for docs sessions — same data source, no new instrumentation, answers the Onboarding-entry question directly; (2) cross-check GA's total against raw CDN/server logs for the same period to size the script-blocking undercount for this audience — a day of work, not six weeks; (3) only then consider a first-party or proxied analytics script if (1) and (2) show it's actually load-bearing for a decision. A product-side event (opt-in CLI telemetry for install completion and first real command) is the one piece of new instrumentation actually worth building, and it's aimed at the tool itself, not the docs site — build it because it answers Onboarding and Integration, not because the agency's traffic-quality argument demands it.

## Gaps

- **Awareness** — `inferred`. No self-reported first-touch source exists. Cheapest fix: a one-field "how did you hear about us" on install or first `cindershell` invocation, not a survey project.
- **Onboarding** — `not instrumented`. Needs (a) the GA page-level breakdown described above, and (b) opt-in CLI telemetry for install completion and first successful real-target command. Both are days of work against tools you already run.
- **Integration** — `not instrumented`. Needs a way to see Cindershell referenced in a CI run vs. only a local shell — likely a CLI-side flag or environment check already available in most CI systems.
- **Production** — `not instrumented`. Needs account/workspace-level rollup (even something as blunt as license key or install ID) to see sustained use over time rather than one-off runs.
- **Advocacy** — `not instrumented`, and will likely sit below the 30-event floor for a long time — publish it as a dated raw list once anything exists, not a rate.
- **Buyer lane** — undetermined; see above. Confirm the sales motion before the next re-read, since it may require adding a whole lane rather than a signal.
