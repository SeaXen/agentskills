# Rotate a signing key without dropping in-flight jobs

Signing keys are never swapped in place — they're rotated through a brief window where **both the old and new key validate successfully**, so nothing already running gets rejected mid-job. The only irreversible step is revoking the old key; everything before that is safe to pause or reverse.

## Before you start

- Note your current active key ID (Dashboard → Security → Signing Keys, or `solvang keys list`).
- Know your longest possible job duration. You'll use it to size the overlap window in Step 4 — this is the number that actually prevents dropped jobs.
- You need the `keys:write` permission. No maintenance window is required; this procedure is designed to run against live traffic.

## Steps

**1. Create the new key without activating it for signing.**

```
solvang keys create --label "rotation-$(date +%Y-%m)"
```

This returns a new key ID and secret with status `pending`. Nothing changes yet — existing traffic still signs and verifies with the old key only.

**2. Enable the new key for verification, alongside the old one.**

```
solvang keys enable-verification <new-key-id>
```

The API now accepts signatures from *either* key. This is the dual-validation window — it's what lets you roll new key material out gradually instead of flipping a switch.

**3. Roll the new key into your signer config.**

Update the secret in your app config / secrets manager and deploy to your workers. Do this as a normal rolling deploy, not all-at-once — because of Step 2, workers still on the old key and workers already on the new key succeed side by side during the rollout.

**4. Wait out the overlap window, and confirm it with data, not the clock.**

Check the "requests signed by key" metric (Dashboard → Security → Signing Keys, or `solvang keys usage <old-key-id>`) until it reads zero. Then wait an additional period equal to your longest job duration plus a buffer — a job that *started* signing with the old key before your rollout finished can still be in flight.

Before moving on, confirm directly:

```
solvang jobs list --signed-with <old-key-id> --status in_progress
```

This must return empty. If it isn't, don't proceed — those are exactly the jobs this procedure exists to protect.

**5. Revoke the old key.**

```
solvang keys revoke <old-key-id>
```

This is the irreversible step. There's no "undo" — only issuing a brand-new key. Do it only after Step 4's check comes back empty.

**6. Verify.**

```
solvang keys list
```

Should show exactly one active key, with zero verification errors on it since the revoke.

## Troubleshooting

**Signature errors right after Step 5.** You revoked before every worker had picked up the new key, or before an in-flight job cleared. Immediately run `solvang keys enable-verification <old-key-id>` to re-open verification — this is safe and reversible — then find the stale workers (usually one that didn't restart during the rolling deploy) and re-run Steps 3–5.

**A worker is still signing with the old key well after deploy.** Some processes cache the signing secret at boot rather than re-reading it. Restart that worker rather than waiting for it to pick up the new value.

**A queued job fails after the old key is revoked.** It was enqueued before rotation and its signature was generated by a worker holding the old secret at dequeue time, not enqueue time. Re-enable the old key (as above), let it drain, then retry the revoke once `jobs list --signed-with <old-key-id> --status in_progress` is empty again.
