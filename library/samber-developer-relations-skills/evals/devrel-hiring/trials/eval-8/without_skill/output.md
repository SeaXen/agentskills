# 30-60-90 Day Plan — Developer Advocate, Overtone

**Start date:** March 2

Each phase below produces evidence — a number, an artifact, or a decision — not just a list of things done. Overtone already has usage data on ~400 self-serve teams; this plan uses it as the baseline instead of treating the first 90 days as pure ramp-up.

## Month 1 (Days 1-30): Learn the product, the users, and the baseline

**Objective:** Understand where self-serve teams get stuck, and establish the numbers this role will be measured against.

- Integrate Overtone's own API using only the public docs by day 5, with no internal help. Log every point of friction.
- Shadow 5 support tickets and 3 sales or onboarding calls involving self-serve teams.
- Interview 6 people: Head of Product, 2 engineers on the core API team, Support lead, PLG/growth lead, and one self-serve customer.
- Audit existing developer-facing assets — docs, blog, changelog, community channels, GitHub presence — and produce a one-page gap list.
- Pull baseline metrics: docs traffic, community activity (if any), blog subscribers, time-to-first-successful-API-call for new self-serve signups.
- Get access to the docs repo, blog CMS, support queue, community channel, and GitHub org.

**Deliverable (day 30):** A short baseline report covering the state of developer content and community, the top 5 friction points found during onboarding, and the metrics this role will report against for the next 60 days.

## Month 2 (Days 31-60): Ship content and fix one real friction point

**Objective:** Produce visible external output and one concrete fix, not attendance at an event.

- Publish 2 technical blog posts built directly from month 1's friction points (e.g., an integration walkthrough, a common failure mode explained), reviewed through the standard docs process.
- File and drive to resolution at least 1 docs or product fix found during onboarding (a broken example, a missing error message, an unclear setup step).
- Submit 2 conference or meetup talk proposals tied to observability or API tooling. Submission is the deliverable this month, not attendance.
- Own one recurring developer-facing channel — community office hours or a public release-notes cadence — with a stated response-time target (e.g., first response under 24 hours).
- Stand up a lightweight feedback loop: a form or tagged channel where self-serve users flag docs or API issues, triaged weekly to the right team.

**Deliverable (day 60):** 2 published posts with tracked pageviews and referral traffic, 1 shipped fix with before/after evidence, 2 CFPs submitted, and a feedback channel with at least one completed weekly triage cycle.

## Month 3 (Days 61-90): Own a metric, not "the community"

**Objective:** Take end-to-end ownership of one developer-engagement metric, with a plan to grow it.

- Agree with the VP, by day 65, on one metric to own going forward — e.g., docs-to-activation conversion, community response time, blog-to-signup referral, or monthly active community members.
- Set a target for that metric based on the month 1 baseline.
- Run one experiment against it (a docs restructure, a new onboarding guide, a community event) and report the result — including if the number didn't move.
- Deliver one of the submitted conference talks, or confirm a date if the event falls after day 90.
- Present a first-quarter report to the VP: baseline vs. current metric, content shipped, fixes landed, and a recommendation for next quarter's focus (double down on docs, invest in a community platform, hire a second DevRel — whichever the evidence supports).

**Deliverable (day 90):** One owned metric with a documented before/after, and a written recommendation for what the role should focus on next.

## Check-ins

- Weekly 30-minute 1:1 with the VP: blockers, what shipped, what's next.
- Formal review at day 30, 60, and 90 against the deliverables above.
