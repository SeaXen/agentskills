Verdict: the boundary mostly holds, but two of the five items are landmines. Fix those before you announce.

**✅ SAML/SSO, RBAC, audit logging — solid, keep as is.**
This is the standard, well-precedented open-core cut (GitLab, Vault, Grafana, Sourcegraph all draw the line here). It gates *governance/compliance*, not core functionality — nobody self-hosting a feature-flag server for a side project or small team needs SSO to get value from the product. The orgs that need it are already budget-holders paying for other compliance tooling elsewhere. This is a scale/maturity trigger, not a "feature prison."

**⚠️ Bulk CSV export of flag history — check which side of a rug-pull you're on.**
Exporting your own operational data doesn't read as a compliance feature to users — it reads as data lock-in, and self-hosters feel entitled to their own data. Two different situations here, and you need to know which one you're in before you announce:
- If export doesn't exist today and you're introducing it Enterprise-only, that's fine — you're not taking anything away, just shipping a new paid convenience feature (comparable to GitHub/Datadog export limits).
- If any export path exists today (even a "click view, copy the table") and you're removing/gating it, that's the "sudden rug pull" anti-pattern — previously-available capability moved behind a paywall. That generates exactly the kind of resentment this boundary is trying to avoid.
Either way, market it as a convenience/scale feature, not as compliance — bundling it with SSO/RBAC/audit-log framing overstates what it actually is.

**❌ Kubernetes operator — don't ship this one as written. Two separate problems stack here:**

1. **Adoption-funnel risk.** An operator is deployment tooling, not governance. A meaningful slice of your 2,000 self-hosting orgs is exactly the audience that deploys via Helm/operator — that's often *how* they got to "self-hosting" in the first place. Gating it means a new org evaluating you on k8s either hand-rolls raw manifests or pays before they've gotten a minute of product value. That's the "feature prison" anti-pattern: blocking evaluation, not gating a scale trigger.

2. **Ownership/provenance risk — bigger, and the one that can blow up publicly.** You said the operator was written by a contributor at a bank, not by you. Unless you have a CLA that reassigns rights, that contributor licensed their work to the project under the same MIT terms as everything else — you don't have exclusive commercial rights to it just because it lives in your repo. Moving a community-contributed feature behind your paywall without that contributor's consent is precisely the "compete with community-built features by commercializing them" failure mode — the same category of move that torched goodwill in the HashiCorp/Elastic relicensing backlashes, except here it's worse because it's one identifiable person's donated labor, not just a license-text change. Check for a CLA first. If there isn't one, talk to the contributor before announcing — don't find out from a GitHub issue thread.

**Mechanical problem underneath all of this:** if the whole repo stays single-licensed MIT, "putting something behind Enterprise" is not actually enforceable — MIT permits modification and redistribution, so any self-hoster can legally strip a runtime license check out of MIT'd code and ship their own build. GitLab/Sentry-style open-core works because the gated code lives in a *separately licensed* module (proprietary or BSL, an `ee/`-style boundary), never merged into the permissively-licensed tree. If you're planning to gate these features with just a feature flag inside the same MIT codebase, the gate is cosmetic, not a real tier boundary — and for the operator specifically, this is moot until you resolve the ownership question, since you may not have the right to relicense it into that separate module at all.

**Net recommendation:** ship SSO/RBAC/audit-log as Enterprise now — that boundary is right. Hold the CSV export until you've confirmed it isn't removing existing capability, and message it as convenience, not compliance. Pull the Kubernetes operator out of this Enterprise list entirely until you've resolved the contributor's rights — either get their consent, or leave it free and pick something else (e.g., extended audit-log retention, or SLA-backed support) to round out the tier.
