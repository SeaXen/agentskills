## Verdict: not workable as scoped — three separate problems, not one

**❌ Position isn't a filterable dimension in the Search Analytics API.** `dimensionFilterGroups` only accepts `country`, `device`, `page`, `query`, `searchAppearance`. Position is a *metric* returned per row, not a stored value you can filter server-side. There is no request you can send that says "give me only queries averaging position 5-20." You have to pull every query row and filter on the returned `position` field client-side, after the fact.

**❌ "The default response" silently truncates the pull.** Unspecified `rowLimit` defaults to 1000, capped at 25,000, with `startRow` for pagination. A 3,000-page docs site across `/docs/`, `/reference/`, `/blog/` plausibly has 10k-100k+ distinct queries. Taking "the default response" means you get some arbitrary top-N slice with no error or warning that rows were dropped — and since the position filter has to happen *after* the pull (previous point), an incomplete pull means your 5-20 band is built from a random fraction of the real query set, not from it. You must paginate to exhaustion (loop `startRow` in steps of 25,000 until a page returns fewer rows than requested) before filtering.

**❌ The comparison itself doesn't hold up, even with correct data.** This is the real issue, and it's independent of API mechanics:

- GSC impressions count how often *your* pages appeared in results. A query with real search volume that you don't rank for at all generates zero GSC rows — it's invisible to this method entirely. Restricting further to position 5-20 excludes both your position 1-4 winners and everything past 20, so you're summing a deliberately narrow, arbitrary slice and calling it "total docs search demand."
- GSC also drops very low-impression/long-tail queries below an anonymization threshold — exactly the profile of a docs site's query variety (specific error messages, API method names, param combos).
- Keyword-tool volume is a *modeled* monthly-search estimate, independent of whether you rank, and it's notoriously unreliable on niche technical/developer terms — the segment your docs live in is the segment those tools model worst.

Summing a position-bounded, privacy-filtered impression count from one system and diffing it against a modeled volume estimate from an unrelated system doesn't produce a "demand gap." It produces the delta between two incompatible measurement methods, and the sign of that delta isn't even predictable — it can go either direction depending on indexing state, the keyword tool's coverage, and the date range you picked. Putting that number in front of a VP as "the gap" will not survive a second person checking the methodology.

## What to actually build

1. **Pull everything, then filter.** `dimensions=['query']` (add `'page'` only if you need per-URL breakdown), `rowLimit=25000`, loop `startRow` to exhaustion, over a stated fixed window (e.g. last 3 or 6 months — GSC caps history at 16 months). Note `dataState` defaults to `final` (excludes the last ~1-2 days) — state that explicitly rather than leaving it implicit.
2. **Filter position 5-20 client-side** on the returned `position` field. That's a legitimate, useful report on its own — "striking distance" queries, a real optimization target list. Label it exactly that: *queries you already rank for, just off page 1*. Don't call it demand.
3. **Don't sum it against keyword-tool volume.** If the actual ask is "how much demand are we missing," that's a different exercise: take queries where GSC shows zero or near-zero impressions (you don't show up at all) and size *those* with the keyword tool, since GSC structurally can't tell you anything about queries you don't appear for. Report the two as separate, clearly labeled numbers — "impressions on ranking queries, position 5-20" and "estimated volume on non-ranking target queries" — never blended into one figure.
4. **This is out of scope for docs-seo anyway.** That skill (`skills/docs-seo/SKILL.md`) handles indexability, canonicals, templates, and internal linking — it explicitly refuses query-targeting and demand-sizing work and routes it to `developer-keyword-research`. Its own failure-modes table calls this exact pattern out by name: *"Estimated query data — third-party volume numbers for technical queries → fix: Search Console, or an explicit 'not verified'"*. That's a direct flag against blending the two sources the way this plan does. Run the demand-sizing piece through the keyword-research skill instead, and keep the docs-seo audit to what Google can actually crawl, index, and canonicalize.

**One-line answer for the VP-facing deck:** report striking-distance impressions and unmet-demand volume as two separate, labeled bars — not one number claiming to be "total demand."
