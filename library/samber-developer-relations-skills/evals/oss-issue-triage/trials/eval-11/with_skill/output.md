Applying `oss-issue-triage`'s Step 5 (duty design) and the failure-modes table — this exact situation is the skill's named "dormant rotation" case, with a documented worked example (Fedora's BugZappers) that matches your setup almost line for line: named volunteers, a documented charter, a biweekly meeting — all present, all quietly stopped, and the project's own page still advertised it as live. The skill's verdict on that pattern: **a rotation that exists only on paper is worse than no rotation**, because reporters expect a response that won't come, a would-be contributor sees a process to join instead of a gap to fill, and maintainers can't see the failure from inside since every artifact still exists. Re-announcing the same rota unchanged reproduces that exact failure — it fixes the visibility problem for one release cycle and then decays silently again, for the same reason it decayed the first time: nothing raises an error when a shift is skipped.

Before you write the announcement, two things need checking, not assuming:

1. **Confirm the six people first, privately, before naming them in public again.** Six months is long enough that someone may have left the project, changed jobs, or lost the bandwidth. Publishing a name that's no longer accurate is a worse signal than publishing nothing.
2. **Run the baseline before promising a response target.** Six-plus months without triage almost certainly means the backlog and untriaged share have grown since whatever number justified the original promise. Check current open count, oldest untriaged item, and untriaged share before repeating any "we respond within N days" line — publish what today's capacity supports, not the number from last year.

What to add to the announcement itself, beyond the reminder:

- **Say the gap out loud.** Don't resume as if nothing happened — state that triage lapsed since March and the call stopped, and that this is a relaunch, not a nudge. Silent resumption teaches nobody anything about why it'll hold this time.
- **Name a backup per shift, not just the primary.** This is the one mechanical change that separates the pattern that survives (Mozilla's rotation) from the one that doesn't (Fedora's). Add "if the primary misses their week, backup covers it" as a written rule, not an assumption.
- **Add a liveness check someone can actually see.** A rota with no visible signal when a shift is skipped will decay the same way again. Pick one cheap, checkable thing — e.g., untriaged-issue count pinned somewhere, or "if nothing's labeled by day 3 of the shift, the backup steps in" — so a missed week produces a visible symptom instead of silence.
- **Name one person accountable for the rotation's health**, separate from the six rotating triagers — someone whose job is noticing "nobody's covered the last two weeks," not doing the triage itself. Right now that job belongs to nobody, which is exactly how it went a year unnoticed.
- **Decide what happens to the backlog that piled up during the gap**, and say it in the same announcement. Restarting a weekly rotation straight into six months of unattended backlog will drown week one. Either scope week one as a dedicated catch-up pass, or explicitly bound what the rotation covers going forward (e.g., new issues only, backlog handled separately) — don't leave it implicit.
- **Ask why the biweekly call actually stopped before just re-scheduling it.** If it lapsed because there was no queue view and no async pre-triage — so it felt like unstructured overhead rather than decision-making — restating the same meeting format will produce the same slow death. Fix the structure (a queue view, async pre-triage in a thread beforehand) or the call is next year's version of this same problem.
- **Link the rota from CONTRIBUTING.md and the issue templates**, if it isn't already, and set a review point (quarterly, or immediately after anyone joins/leaves) so drift gets caught in weeks, not a year.

One thing to flag rather than paper over: if the honest answer to "are these six people still active with real hours" comes back thin, the credible move per the skill is to shrink the rotation or lengthen the shift to fit real current capacity, not republish the original roster and hope it holds — an aspirational schedule from six volunteers who no longer have three hours a week is the same failure with a new announcement date on it.
