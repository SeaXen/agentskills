# Versioning: draft sections

**Decisions to confirm:**
- ⚠️ **`2026.04` is not a valid Cargo version.** Cargo needs `MAJOR.MINOR.PATCH` and rejects leading zeros. The version is `2026.4.0`, and "2026.04" stays as the human-facing release name.
- ⚠️ **Cargo reads `2026.4.0` → `2026.10.0` as a compatible upgrade.** A dependency written as `hollowmere = "2026.4"` picks up every later 2026 release. Breaking changes therefore ship only when the year changes, which is the only way to keep Cargo resolution honest.
- ℹ️ **I read "runtime" as the Rust toolchain contract (MSRV).** If you meant async executor support for `hollowmere-async`, tell me and I'll add it.

## Version numbers

All four crates (`hollowmere-core`, `hollowmere-derive`, `hollowmere-async`, `hollowmere-cli`) share one version. That version is the release.

### Format

- Use `YYYY.M.P` in every `Cargo.toml`, git tag, and changelog heading. Example: `2026.4.0`.
- `YYYY` is the year of release and `M` is the month, with no leading zero.
- `P` is the patch counter, starting at `0`.
- Call a release by its calendar name, "hollowmere 2026.04". It means Cargo version `2026.4.x`.
- Ship at most one `.0` release per month.

### What each part means

| Part | Changes when | Allowed content |
| --- | --- | --- |
| `YYYY` | First release of a new calendar year | Breaking changes |
| `M` | Each monthly release | New features, deprecations, MSRV bumps, experimental API changes |
| `P` | Fix between monthly releases | Bug fixes and security fixes only, with no new public API and no MSRV bump |

### Lockstep rules

- Publish all four crates at the same version on every release, including crates with no changes.
- Pin sibling crates exactly: `hollowmere-core = "=2026.4.0"` in `derive`, `async` and `cli`. The derive macro emits code that depends on the exact `core` it was built with, so a mixed set is unsupported.
- Release a patch for all four crates, never for one.

### Support questions

- Ask for `cargo tree -i hollowmere-core` or `hollowmere --version`. Every crate reports the same number.
- Treat a report where the four crates disagree as a user dependency problem, not a bug.

### Migration from the old numbers

- The first calendar release is the next Cargo major for every crate:
  - `core` and `derive` go from `0.14` to `2026.M.0`.
  - `async` goes from `0.6` to `2026.M.0`.
  - `cli` goes from `1.2` to `2026.M.0`.
- Never publish a lower number than the current one. `cargo install hollowmere-cli` picks the highest version, so anything below `1.2` would be ignored.
- Land any pending breaking changes in this first release.
- Add a README table mapping the old per-crate versions to the first calendar release.

## Breaking changes

### Rule

- Breaking changes ship only in the first release of a calendar year, such as `2027.1.0`.
- Breaking changes never ship in a monthly or patch release.
- The one exception is a soundness or security fix with no compatible form. Ship it as a patch, label it **BREAKING (soundness)** in the release notes, and yank the affected earlier versions.

### What counts as public API

**Library crates (`core`, `derive`, `async`):**
- Items reachable from the crate root that are not behind the experimental cfg or `#[doc(hidden)]`.
- Trait bounds and associated types.
- Macro input syntax, including every attribute `derive` accepts.
- Cargo feature names.

**`hollowmere-cli`:**
- Subcommands and flags.
- Exit codes.
- Config file schema.
- Machine-readable output, such as `--json`.
- Human-readable text output is not public and may change in any release.

**Never public:** code generated by `derive`, items marked `#[doc(hidden)]`, and internal modules.

**Not breaking by themselves:** MSRV bumps (see Runtime) and adding enum variants to types marked `#[non_exhaustive]`.

### Deprecation

1. Mark the item `#[deprecated(since = "2026.4.0", note = "use X")]`. For CLI flags, print a warning to stderr.
2. Keep it working for at least three months and through the end of the year.
3. Remove it only in a January release.
4. List every removal in that release's migration section, with a before and after snippet.

### Experimental APIs

Experimental APIs are excluded from every promise above.

- Gate them behind a cfg flag, not a Cargo feature. Enabling it needs `RUSTFLAGS="--cfg hollowmere_unstable"`. A Cargo feature would be switched on for the whole dependency graph by any one crate that asks for it. A cfg flag forces the end user to opt in.
- Mark each item in rustdoc as experimental, with the release it was added in.
- Experimental APIs may change or disappear in any `YYYY.M.0` release without deprecation. They stay stable within a patch series.
- Release notes list experimental changes under their own heading, never under Breaking.
- Promote an experimental API to stable in a monthly release. Once stable, it follows the full policy.
- Keep experimental items out of `hollowmere-cli` flags and the config schema. Those are always stable or absent.

## Runtime

### MSRV

- MSRV is declared in `rust-version` in all four crates and is identical across them.
- MSRV is the Rust stable release that is at least six months older than the release date. Rust ships every six weeks, so this is a window of about four releases.
- MSRV may rise only in a `YYYY.M.0` release, never in a patch. A patch release keeps the previous MSRV.
- MSRV bumps are not breaking changes. They are allowed in any monthly release.
- State the MSRV in the release notes of every `.0` release, with the line "MSRV: unchanged" or "MSRV: 1.xx (was 1.yy)".
- Never raise MSRV above the rule just because a new compiler feature is convenient. Wait for the window.
- The next calendar release may jump once from 1.78 to the rule's value. After that, the rule applies.
- CI runs the full test suite on the declared MSRV and on current stable.

### Supported releases

- Only the latest `YYYY.M` line gets fixes. Older months do not receive patches.
- Security fixes also go to the last release of the previous year, for twelve months after the new year's first release. This gives users on `2026.*` time to move to `2027.1.0` without running unpatched code.

### Platforms

- Tier-1 targets for the binary (`hollowmere-cli`) are the ones CI builds and tests on every release. Name them in the README.
- Dropping a tier-1 target is a breaking change and follows the January-only rule.
