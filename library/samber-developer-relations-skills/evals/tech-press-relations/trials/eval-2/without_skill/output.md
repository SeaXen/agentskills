# Sablefish Press Release — Draft

**A note before the release text (read this first, strip it before sending):**

I wrote this as a data story, not a product announcement, because that's the only honest story available. The dataset — six months, 3,400 teams, breaking changes vs. version bumps — is a genuinely pitchable "State of X" report in the mold of Stripe's or Intercom's annual benchmarks. It just isn't a press release yet, because nobody has run the numbers. I can't put a percentage in a press release that no one has calculated — if a journalist (or a competitor, or a customer) asks for the methodology or the raw distribution, a made-up number falls apart immediately and does more damage than no story at all.

So the release below is complete except for the bracketed stats. Filling them in is a data-pull, not a research project — see the query list at the bottom. Once the numbers are in, this is ready to send.

## What to run before this goes out

Three queries turn this from a draft into a sendable release. Pick the one or two results that are genuinely surprising — a data story lives or dies on one good number, not five average ones.

1. **Headline stat:** of all changes classified as breaking, what share shipped without a major-version bump (or equivalent)? This fills the headline and lede.
2. **Trend:** did that share go up, down, or stay flat over the six months? A worsening trend ("breaking changes are increasingly shipping silently") is a stronger hook than a flat one.
3. **Segmentation, pick one:** breakdown by change type (removed field vs. changed type vs. removed endpoint — which is most common?), or by team size, or by whether the team has a published changelog. Whichever produces the most counterintuitive result is the one to lead with instead of the headline stat, if it's stronger.

If the numbers turn out boring — say, 8% instead of a shocking majority — that's still a usable story ("even disciplined teams get this wrong 1 in 12 times"), but don't round up or cherry-pick the six-month window to flatter the result. Tech press fact-checks data claims, and a debunked stat costs more credibility than the five months of silence you're trying to fix.

Once the numbers are in, the pitch-email version of this (for reporters, ~150 words, different from the release itself) should lead with whichever single stat is most specific — "[XX]% of breaking API changes ship with no version bump" beats "New data on API versioning" as a subject line every time.
