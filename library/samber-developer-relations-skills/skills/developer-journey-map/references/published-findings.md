# Published findings

Where every number and named model in this skill comes from, and which ones are this skill's own defaults. Read this before quoting a figure to a user or defending a threshold.

The short version: the journey _vocabulary_ is published and citable. Per-stage _conversion rates_ are not: the figures in circulation are single-company anecdotes with incompatible stage definitions, so no "normal" discovery-to-production rate can be quoted. Every rate in a map has to come from the product's own data, and every comparison has to be against the same map's previous version.

## Self-set baselines

None of these has a published study behind it. They are this skill's defaults, chosen because they make a map decidable. Present them as adjustable starting points, and say so when a user asks where the number comes from.

| Baseline                                   | Value                                                                       | Why this number                                                                                                                                                                             |
| ------------------------------------------ | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Stage count                                | 5-7                                                                         | Fewer hides the leak inside a stage; more produces stages nobody can name an exit event for                                                                                                 |
| Signal coverage to pass                    | 60% of stages carrying a real current value                                 | Enough to compute at least one honest conversion rate while leaving room for the genuinely dark early stages                                                                                |
| Completed-journey interviews               | 5-8                                                                         | Matches the panel size usability research settles on; enough to hear a pattern twice                                                                                                        |
| Abandonment interviews                     | 3                                                                           | The realistic recruiting ceiling, and three is usually enough to relocate an assumed leak by one stage                                                                                      |
| Leaks nominated per cycle                  | Exactly 1                                                                   | Three priorities is none, and the earliest-owned rule already produces a unique answer                                                                                                      |
| Owners outside DevRel                      | At least 1                                                                  | A map where DevRel owns every row was never negotiated with the teams that own the surfaces                                                                                                 |
| Re-read horizon                            | 90 days, and always after a launch, pricing change, docs rewrite or new SDK | Two quarters is long enough for a surface to have moved under the map                                                                                                                       |
| Signals per stage                          | Exactly 1                                                                   | More turns the map into a dashboard and hides the decision                                                                                                                                  |
| Stage-model effort and efficiency ordering | API arc, OSS funnel, AAARRRP, Revell, unsourced default                     | Reasoned from what evidence each model's boundaries need before they can be counted, and meant to be re-ranked against what a team already instruments                                      |
| No value ordering across stage models      | deliberate                                                                  | A model's value is decided entirely by whether its terminal stage is the funded end state, so a fixed order would be false precision - the end state deletes models instead of ranking them |

The small-N floor - publish the raw list with dates below roughly 30 events in a period instead of a rate - is a statistical convention, not a DevRel finding. Treat it as a discipline, not a citation.

## Claims to refuse

- **Any per-stage conversion benchmark from another company.** The figures circulating, including the five-stage API model's own numbers, are single-company anecdotes with no stated methodology. A map that compares itself to one is comparing across different audiences, product maturity and stage definitions at once.
- **A single global self-serve activation percentage**, such as the unattributed "20-40%" figure. No instrumented, milestone-based, developer-tools-specific study publishes one - the developer-tools survey above explicitly declines to give one, because the milestone differs by product. The nearest real numbers are a self-reported survey's median-to-average band (25-36%, see the sourced claims above) and an instrumented day-7-retention proxy under a different definition of activation entirely (2.1% median, 7% top quartile); the popular round figure collapses two different metrics into one number. Cite the actual source and its caveats, never the bare rounded figure, and never as a target.
- **Emotion scores per stage.** Generic journey maps carry them; at developer volumes they are not measurable, and they displace the columns that carry accountability.
- **Absolute traffic numbers from a third-party analytics script on a developer surface.** The Plausible measurement above means a docs-site session count is roughly measuring the non-developer half of the audience, and the blocking rate varies by page. A Linux install page is blocked far harder than a pricing page. Ratios inside one source survive; absolutes do not.
- **An attribution number presented without its bias direction.** Self-reported attribution over-counts memorable touches. Tagged links inflate "direct". Influenced pipeline over-counts by construction.
- **A rate computed from fewer than about 30 events.** Publish the dated raw list instead.

## Practitioner voices

- Hathaway on what to count instead of stars: outside contributions, forks, clones, downloads, pull requests and conversations - and "developer communities are not one single number to rule them all".
- Thengvall on the revenue question: "I don't believe DevRel or Community teams should ever (_EVER!_) have sales metrics to gauge their success. It muddies our work too much and changes what should be a genuine relationship into one that revolves around money." The opposing position - influenced pipeline, explicitly shared and never presented without the word "influenced" - is equally defensible; which one applies depends on who funds the team.
- Hammerly on who should write the friction log: new hires, because they lack the inside knowledge that lets veterans route around rough spots without noticing.
- Fogg on where to spend the effort: "simplicity changes behavior" - raise ability rather than pump motivation, because motivation arrives in waves and crashes.

## Named frameworks and their limits

Two frameworks are named in this skill, and each answers a different question:

- **A stage model** (Revell, AAARRRP, Orbit, the API five-stage arc, the OSS contributor funnel) answers _where in the journey a developer is_. It says nothing about owners, exit events or why a stage fails.
- **B=MAP** answers _why one already-chosen stage leaks_ - motivation, ability or prompt. It cannot rank stages against each other, so it runs after the leak is picked, never instead of picking it.

The table shape itself comes from generic customer-journey mapping; everything developer-specific sits in those two frameworks, and the quality gate in the skill body is self-set.
