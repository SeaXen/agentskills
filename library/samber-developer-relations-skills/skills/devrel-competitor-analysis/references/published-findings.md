## Named methods you may attribute

- **CORE situational-analysis framework, Relationships quadrant** (Matthew Revell / Hoopy, published on developerrelations.com). Asks, per competitor: how the developer community perceives it, its relative strengths, and specifically what its developer-relations approach is. Classifies entities as market leaders, challengers, niche players, shooting stars. An earlier version of the page also instructed the analyst to attend the competitor's meetups and build something on their product; that instruction is no longer on the live page, so check an archived copy before quoting it.
- **Pronovix developer-portal benchmark**: map ~6 focus areas of the developer journey, score 130+ practices grouped into ~2 dozen enablers, then benchmark against a best-in-class standard or named competitors. Published on a Tier-1 bank case study covering only the publicly accessible portal. Laura Vass's accompanying argument is the strongest published pushback against benchmarking-as-checklist: the useful question is what your own portal provides and signals, and to whom.
- **Stack Overflow tag comparison** (Square practitioner talk, developerrelations.com): compare question volume, response time and word frequency across vendor tags. This is the source for treating Q&A tags as a sixth signal surface.
- **Matt Makai's gap-to-hire chain** (DevRelCon New York 2024, "Measuring progress in developer relations"): Twilio's PHP content stopped when its authors left while Nexmo/Vonage kept publishing; PHP signups were near zero; the verdict was to hire for PHP content. The most fully documented close-the-gap decision in the field. Two lessons from the same talk: a competitor's spiky output can be deliberate launch cadence rather than inconsistency, and an unfamiliar competitor tactic is worth validating by contacting the company and asking whether it worked.
- **Demand-side competitive set** (Bob Moesta, Jobs to be Done): the real rival is what the customer would use if your product vanished. Applied to peer-set framing, this surfaces documentation, a forum answer or a hand-rolled script as competitors, not only funded vendors.
- **Teardowns produce hypotheses, not patterns** (Elena Verna): validate an external tactic against your own data before adopting it.

Do not force-fit the wider strategy canon that travels with these sources - Porter's generic strategies, Helmer's 7 Powers, Blue Ocean. They answer where a durable advantage lies, which is a different question from what a rival does for developers that you do not.

## This skill's own baselines

None of the following is an industry standard. Present each as the bar this analysis sets for itself, and change it when the user has a reason to.

| Baseline                                    | Value                                                                 | Why this value                                                                                                                           |
| ------------------------------------------- | --------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Peer-set size                               | 3-5                                                                   | Beyond five, each added peer dilutes the depth of every column and the analysis stops converging on a plan                               |
| Sampling window                             | 12 months                                                             | Shorter windows read a launch or conference season as a trend                                                                            |
| Community-volume sampling                   | 4 separated weeks                                                     | Chosen to survive burstiness rather than measured                                                                                        |
| Symmetry, traceability, verdict coverage    | 100% each                                                             | Definitional rather than empirical: a ragged row is not comparable, an unsourced cell is not re-derivable, an unjudged gap is not a plan |
| "At least three high-impact, low-cost gaps" | 3                                                                     | A judgement call about when a peer set is mis-picked, not a measured threshold                                                           |
| Freshness                                   | nothing older than the current quarter                                | Matches the docs and content re-run cadence below                                                                                        |
| Re-run cadence                              | quarterly for docs and content, twice yearly for community and events | A working default; the event triggers alongside it matter more than the clock                                                            |

## Contested or unconfirmed

- **GitHub's public events firehose reportedly stopped emitting most star, pull-request and issue events**, which would silently corrupt any cadence metric derived from a firehose-based aggregator. Reported on OSSInsight's own site notice and unconfirmed by the platform itself. Collect star, PR and issue counts from the repository API directly when the number has to be trustworthy, and date-stamp anything taken from an aggregator.
- **Who owns this work in a startup.** The documented pattern is the DevRel lead doing it personally with a self-built tool, from a single case. Treat it as a hypothesis rather than a norm.

## Never assert

- That a competitor's private numbers - traffic, budget, team size, revenue per surface - are known. Every one of them is a proxy; label it in the cell.
- That a DevRel competitive-benchmarking standard exists. The three named methods above are each one company's or practitioner's method, and their effect on outcomes is untested.
- That a benchmark is a program. In the one fully documented case the business question came first and the competitor data was one input among several.
