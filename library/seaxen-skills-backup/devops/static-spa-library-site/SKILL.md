# Static SPA Library Site from Content Folders

Build a dark-themed static SPA library site when you have:

- A hierarchy like **chapter → hub → topic**, where each topic has a `*.png` (infographic) and `*.md` (notes)
- A canonical chapter list (e.g. Davidson 25th Ed, 32 chapters) where some are built and some are "coming soon"
- A user who wants it deployable as both Docker and Vercel, accessible to LAN, with a per-chapter SPA layout

The pattern that emerged and was iteratively polished: **sticky compact header + per-chapter dropdown + 2-column topic sidebar + main pane with PNG+MD content + topics.json manifest**.

## When NOT to use (route elsewhere)

- **Single-repo product marketing page on GitHub Pages** (`docs/index.html`, install hero, screenshots): use `github/github-operations` → `references/github-pages-product-landing.md`. No chapter SPA, nginx container, or `topics.json` needed.

## When to use

- User has a content folder like `/mnt/tb/<subject>/<chapter>/<hub>/<topic>/{topic.png, topic.md}` or the flat variant `<hubnum.idx>-<slug>.{png,md}`
- Wants a website to view all chapters at once
- Wants it styled dark-theme / telemetry-aesthetic
- Wants Docker deploy on a specific port AND Vercel deploy
- Wants to embed Notion links alongside local content

## When NOT to use

- The content is small (< 5 items) — just a static page or README is enough
- User needs a CMS / database — use a real SPA framework (Next.js, Astro)
- User needs user auth / per-user state — this is a static read-only site
- The user wants a server-rendered React app — different architecture

## Architecture

```
site/
├── index.html                # Landing: header + chapter grid (5 cards)
├── <chapter-slug>/
│   ├── index.html            # SPA shell: sidebar (topics) + main (topic content)
│   ├── topics.json           # Manifest: all topics pre-rendered as HTML + paths
│   └── diseases/
│       └── <topic>/{topic.png, topic.md}    # Source assets copied here
├── vercel.json               # static serving config + cleanUrls
└── README.md
```

Plus Docker setup at repo root:
- `Dockerfile` — `FROM nginx:alpine`, copy `site/` to `/usr/share/nginx/html`, expose 80 (container-internal), use `docker/nginx.conf`
- `docker/nginx.conf` — gzip on, 7-day cache for images, 1-hour cache for HTML

## Content rendering — auto-synthesize visual elements from MD structure

The build script's `render_md_to_html` reads each topic's MD and pre-renders to HTML for the SPA. The renderer fires `render_mindmap_md()` / `render_flowchart_md()` **only** when an explicit `mermaid` / `mindmap` / `flowchart` code block is present. When the source MD lacks those blocks (common in chapters that predate the mermaid support, or chapters generated by other agents), topics render as plain text with no visual.

**The fix is a synthesis fallback in the build script's markdown renderer** — if no mermaid block was found, extract the H1/H2/H3 structure and build a mindmap from the headings automatically. This guarantees every topic gets a visual, regardless of source.

```python
# In render_md_to_html():
found_mermaid = False
# ... inside flush_code() when code_kind in ("mindmap", "flowchart", "graph"):
#     found_mermaid = True

def _synthesize_mindmap_from_headings(md_text: str) -> str:
    """Build a mindmap from H1/H2/H3 when source has no mermaid block."""
    headings = []
    for line in md_text.split("\n"):
        m = re.match(r"^(#{1,6})\s+(.+?)\s*$", line)
        if m:
            level = len(m.group(1))
            text = re.sub(r"\*\*(.+?)\*\*", r"\1", m.group(2).strip())
            text = re.sub(r"\*(.+?)\*", r"\1", text)
            text = re.sub(r"`(.+?)`", r"\1", text)
            if len(text) > 80:
                text = text[:77] + "..."
            headings.append((level, text))
    if len(headings) < 2:
        return ""
    root = ""
    items = []
    for lvl, txt in headings[:40]:
        if lvl == 1 and not root:
            root = txt
            continue
        if lvl in (2, 3):
            items.append((lvl, txt))
    if not root and items:
        root = items.pop(0)[1]
    if not root:
        return ""
    lines = ["mindmap", f"  root(({root}))"]
    for lvl, txt in items[:30]:
        indent = "    " if lvl == 2 else "      "
        lines.append(f"{indent}{txt}")
    return render_mindmap_md("\n".join(lines))

# At the end of render_md_to_html(), after flushing all blocks:
if not found_mermaid:
    synth = _synthesize_mindmap_from_headings(md_text)
    if synth:
        out.append('<h2>Topic Overview</h2>')
        out.append(synth)
```

**Verification pattern:**

```python
# Check synthesis coverage after build — every topic should have a mindmap
for ch_dir in site.glob("[0-9]*-*/"):
    d = json.load(open(ch_dir / "topics.json"))
    synthesized = sum(1 for t in d["topics"] if "Topic Overview" in t["html"])
    explicit    = sum(1 for t in d["topics"] if 'class="mindmap"' in t["html"] and "Topic Overview" not in t["html"])
    print(f"{ch_dir.name}: {synthesized} synthesized + {explicit} explicit")
```

**When to extend this pattern:**
- Synthesis fails on topics with no usable H1/H2/H3 structure (single-line topics, pure tables). These are usually hub-pages, not disease topics — skip them.
- Add a "synthesized" marker in the output so you can tell apart rendered-from-source vs synthesized-from-structure later.
- The same approach works for flowcharts (synthesize from tables with Stage/Type/Severity columns) but the heuristic is less reliable. Mindmaps from headings are the highest-value synthesis.

## Universal search across all topics

The sidebar search filter is per-chapter (hides topics within the current chapter). For 32 chapters × 50-300 topics each, the user needs **global search across all 2,957 topics from a single header input** that jumps directly to the topic in the right chapter.

**Architecture: pre-built flat JSON index + lazy load on first keystroke + scored matches + keyboard nav.**

### 1. Generate the index at build time

```python
def write_search_index(site_data):
    items = []
    for ch_slug, (ch_name, _ch_url, _ch_color) in BUILT_CHAPTERS.items():
        info = site_data.get(ch_slug)
        if not info or info["n_topics"] == 0:
            continue
        ch_num = ch_slug.split("-")[0]
        for hub_num in sorted(info["by_hub"].keys()):
            hub_topics = sorted(info["by_hub"][hub_num], key=lambda t: t["local_prefix"])
            hub_name = info["hub_names"].get(hub_num, hub_num)
            for t in hub_topics:
                title = t["slug"].replace("-", " ").title()
                items.append({
                    "chapter_num": ch_num,
                    "chapter_name": ch_name,
                    "chapter_slug": ch_slug,
                    "hub_num": hub_num,
                    "hub_name": hub_name,
                    "topic": t["local_prefix"],
                    "title": title,
                    "url": f"/{ch_slug}/",
                })
    (SITE / "search_index.json").write_text(
        json.dumps(items, ensure_ascii=False, separators=(",", ":"))
    )
```

Output is ~700KB for 2,957 topics. One fetch on first keystroke, cached in memory after.

### 2. Header input + dropdown panel

```html
<div class="search-box" id="searchBox">

         autocomplete="off" spellcheck="false">
```

```javascript
(function() {
  let idx = null;
  const input = document.getElementById('searchInput');
  const results = document.getElementById('searchResults');
  const box = document.getElementById('searchBox');

  function loadIdx() {
    if (idx) return Promise.resolve(idx);
    return fetch('/search_index.json').then(r => r.json()).then(d => { idx = d; return d; });
  }

  function esc(s) { return s.replace(/&/g,'&amp;').replace(/</g,'&lt;').replace(/>/g,'&gt;'); }
  function highlight(text, q) {
    const i = text.toLowerCase().indexOf(q.toLowerCase());
    if (i < 0) return esc(text);
    return esc(text.slice(0,i)) + '<mark>' + esc(text.slice(i,i+q.length)) + '</mark>' + esc(text.slice(i+q.length));
  }

  function search(q) {
    loadIdx().then(data => {
      const ql = q.toLowerCase();
      const hits = [];
      for (const item of data) {
        const t = item.title.toLowerCase(), h = item.hub_name.toLowerCase(), c = item.chapter_name.toLowerCase();
        let s = 0;
        if      (t === ql)                  s = 100;
        else if (t.startsWith(ql))          s = 80;
        else if (t.includes(ql))            s = 60;
        else if (item.topic && item.topic.startsWith(ql)) s = 70;
        else if (h.includes(ql))            s = 40;
        else if (c.includes(ql))            s = 20;
        if (s > 0) hits.push({item: item, score: s});
      }
      hits.sort((a, b) => b.score - a.score || a.item.title.localeCompare(b.item.title));
      const top = hits.slice(0, 20);
      results.innerHTML = top.length === 0
        ? '<div class="search-empty">No topics match "<strong>' + esc(q) + '</strong>"</div>'
        : top.map(h => '<a class="search-hit" href="' + h.item.url + '?topic=' + encodeURIComponent(h.item.topic) + '">'
          + '<span class="hit-ch">' + h.item.chapter_num + '</span>'
          + '<span class="hit-body">'
            + '<span class="hit-title">' + highlight(h.item.title, q) + '</span>'
            + '<span class="hit-meta">' + highlight(h.item.chapter_name, q) + ' · ' + highlight(h.item.hub_name, q) + ' · ' + h.item.topic + '</span>'
          + '</span>'
          + '<span class="hit-arrow">→</span>'
        + '</a>').join('');
      if (hits.length > 20) results.innerHTML += '<div class="search-more">+' + (hits.length - 20) + ' more matches…</div>';
      box.classList.add('open');
    });
  }

  let debounce = null;
  input.addEventListener('input', e => {
    clearTimeout(debounce);
    const q = e.target.value.trim();
    if (q.length < 2) { results.innerHTML = ''; box.classList.remove('open'); return; }
    debounce = setTimeout(() => search(q), 120);
  });

  // Close on outside click + Escape
  document.addEventListener('click', e => { if (!box.contains(e.target)) box.classList.remove('open'); });
  input.addEventListener('keydown', e => {
    if (e.key === 'Escape') { input.value = ''; results.innerHTML = ''; box.classList.remove('open'); input.blur(); return; }
    const hits = results.querySelectorAll('.search-hit');
    let ai = Array.from(hits).findIndex(h => h.classList.contains('active'));
    if (e.key === 'ArrowDown') { e.preventDefault(); ai = Math.min(ai + 1, hits.length - 1); }
    else if (e.key === 'ArrowUp') { e.preventDefault(); ai = Math.max(ai - 1, 0); }
    else if (e.key === 'Enter' && hits[ai]) { e.preventDefault(); hits[ai].click(); return; }
    hits.forEach((h, i) => h.classList.toggle('active', i === ai));
  });
})();
```

**Key decisions:**
- **Lazy load on first input** — the 700KB index isn't fetched until the user actually types. Saves a request on every page load.
- **Debounce 120ms** — fast enough to feel instant, slow enough to skip fast typers.
- **Score-based ranking** — title-exact (100) > title-prefix (80) > topic-prefix (70) > title-contains (60) > hub (40) > chapter (20). Topic number prefix matching helps find "16.4.2" directly.
- **`<mark>` for highlight** — semantic and styleable.
- **Cap at 20 results + "+N more"** — keeps dropdown usable. Users with 50+ matches need to refine their query anyway.
- **Click goes to `chapter?topic=<local_prefix>`** — the SPA auto-loads that topic from topics.json.

**Pitfalls:**
- **Don't bundle the index into a JS file** — JSON fetch is cached, JS bundle is not. Keep the index a separate `.json` request.
- **Don't use `position: absolute` for the dropdown** — `position: fixed; top: 56px` so it floats below the sticky header and never gets clipped by sidebar overflow.
- **Don't `stopPropagation` on input** — outside-click handler checks `box.contains(e.target)`, so clicks on results also close correctly without needing to stop propagation on the input.

## Build pipeline (Python static generator)

A single script (`scripts/site/build_site.py`) does everything:

1. **Scan chapters/ folder** — find PNG/MD pairs (two patterns: folder-based `<topic>/topic.{png,md}` and flat `<prefix>-<slug>.{png,md}`)
2. **Copy assets** to `site/<chapter>/diseases/...`
3. **Build topics.json** — pre-render every topic's MD to HTML and embed in JSON so the SPA can load instantly via fetch
4. **Write landing page** — chapter grid with preview-strip thumbnails
5. **Write per-chapter SPA HTML** — sidebar with hub-grouped topics + JS that loads `topics.json` and renders the selected topic

`.gitignore` should exclude `site/**/*.png` (they duplicate chapters/) but keep MDs, HTML, and topics.json (needed for download buttons and SPA loading).

**Why both `text-align` and `align-items: center`:** `text-align` only affects inline text content (h2, span, links). `align-items: center` is needed for block-level children like the `.ch-stats` row of pill numbers. Use both together for complete coverage. Verify by spot-checking a chapter card in browser: every line of text should have the same left/right margin to the card edge.

## SPA topics.json manifest pattern

Instead of generating N static HTML files per topic, pre-render all topic HTML into one JSON manifest:

```python
manifest = {
    "chapter": ch_slug,
    "chapter_name": ch_name,
    "notion_url": ch_url,
    "accent_color": ch_color,
    "topics": [
        {
            "local_prefix": "17.1.01",
            "hub_num": "17.1",
            "hub_name": "Functional Anatomy...",
            "slug": "a-a-gradient-and-oxygenation-failure",
            "title": "A A Gradient And Oxygenation Failure",
            "png": "diseases/17.1.01-a-a-gradient-and-oxygenation-failure/topic.png",
            "md": "diseases/17.1.01-a-a-gradient-and-oxygenation-failure/topic.md",
            "html": "<blockquote>...</blockquote><h2>...</h2>..."  # pre-rendered
        },
        ...
    ]
}
(SITE / ch_slug / "topics.json").write_text(json.dumps(manifest, ensure_ascii=False))
```

The SPA then does:

```js
async function loadManifest() {
  const res = await fetch(`/ch-slug/topics.json`);
  MANIFEST = await res.json();
  const t = new URLSearchParams(location.search).get("topic");
  if (t) showTopic(t);
}

function showTopic(localPrefix) {
  const t = MANIFEST.topics.find(x => x.local_prefix === localPrefix);
  // ... render t.html, t.png, t.title into main pane
  history.replaceState(null, "", "?topic=" + localPrefix);
}

function navigateTopic(dir) {
  const i = MANIFEST.topics.findIndex(x => x.local_prefix === CURRENT_TOPIC.local_prefix);
  const ni = i + dir;
  if (ni < 0 || ni >= MANIFEST.topics.length) return;
  showTopic(MANIFEST.topics[ni].local_prefix);
}
```

**Why this beats per-topic HTML pages:**
- One file fetch loads all topics (cacheable, parallel content available)
- Prev/Next navigation is `O(1)` index lookup
- `?topic=<prefix>` URL gives direct linking
- Switching chapters is instant (just load a different JSON)

**Pitfall:** JSON `local_prefix` is the key. If the URL has `?topic=17.1.1` but the JSON has `17.1.01`, it silently fails. Use zero-padded prefixes consistently. If URL doesn't match, fall back to first topic instead of showing the placeholder.

```nginx
  index index.html;
  gzip on; gzip_types text/plain text/css application/json image/svg+xml;

  location ~* \.(html)$ { expires 1h; }

}
```


The **NGINX_CONFIG must listen on 80**, the **container exposes 80**, and the **host port maps to 8855**. Don't put the host port in nginx.conf.

## Iteration loop (screenshot → diagnose → patch CSS)

When user complains "X is too big / not visible / wrong color":

2. **Probe computed styles** for color/visibility:

### 3. Separate mobile search IIFE

Write a second IIFE next to the desktop one. They share `fetch('/search_index.json')` but otherwise don't touch each other's state. Add `if (!input) return;` as the first line — the desktop-only pages (if any) don't have `#searchInputMobile` and would crash otherwise.

```javascript
// ===== Mobile search (separate code, doesn't touch desktop) =====
(function() {{
  const input = document.getElementById('searchInputMobile');
  const results = document.getElementById('searchResultsMobile');
  const box = document.getElementById('searchBoxMobile');
  if (!input) return;                            // <-- critical guard

  let sharedIdx = null, debounce = null, activeIdx = -1, hits = [];

  function loadIdx() {{
    if (sharedIdx) return Promise.resolve(sharedIdx);
    return fetch('/search_index.json').then(r => r.json()).then(d => {{ sharedIdx = d; return d; }});
  }}
  function escHtml(s) {{ return s.replace(/&/g, '&amp;').replace(/</g, '&lt;').replace(/>/g, '&gt;'); }}
  function highlight(text, q) {{
    if (!q) return escHtml(text);
    const i = text.toLowerCase().indexOf(q.toLowerCase());
    if (i < 0) return escHtml(text);
    return escHtml(text.slice(0, i)) + '<mark>' + escHtml(text.slice(i, i + q.length)) + '</mark>' + escHtml(text.slice(i + q.length));
  }}
  function search(q) {{
    loadIdx().then(data => {{
      const ql = q.toLowerCase();
      hits = [];
      for (const item of data) {{
        const t = item.title.toLowerCase(), h = item.hub_name.toLowerCase(), c = item.chapter_name.toLowerCase();
        let s = 0;
        if      (t === ql)                              s = 100;
        else if (t.startsWith(ql))                      s = 80;
        else if (t.includes(ql))                        s = 60;
        else if (item.topic && item.topic.startsWith(ql)) s = 70;
        else if (h.includes(ql))                        s = 40;
        else if (c.includes(ql))                        s = 20;
        if (s > 0) hits.push({{ item, score: s }});
      }}
      hits.sort((a, b) => b.score - a.score || a.item.title.localeCompare(b.item.title));
      const top = hits.slice(0, 30);
      activeIdx = -1;
      results.innerHTML = top.length === 0
        ? '<div class="result-item" style="cursor:default;color:var(--text-dim);">No topics match "<strong style="color:var(--accent)">' + escHtml(q) + '</strong>"</div>'
        : top.map(h => '<a class="result-item" href="' + h.item.url + '?topic=' + encodeURIComponent(h.item.topic) + '">'
            + '<span class="badge">Ch ' + h.item.chapter_num + '</span>'
            + '<span>' + highlight(h.item.title, q) + '</span>'
            + '<span class="crumb">' + highlight(h.item.chapter_name, q) + ' · ' + h.item.topic + '</span>'
          + '</a>').join('');
      results.classList.add('open');
    }});
  }}
  input.addEventListener('input', e => {{
    clearTimeout(debounce);
    const q = e.target.value.trim();
    if (q.length < 2) {{ results.classList.remove('open'); results.innerHTML = ''; return; }}
    debounce = setTimeout(() => search(q), 150);
  }});
  input.addEventListener('focus', () => {{
    if (input.value.trim().length >= 2) results.classList.add('open');
  }});
  document.addEventListener('click', e => {{ if (!box.contains(e.target)) results.classList.remove('open'); }});
  input.addEventListener('keydown', e => {{
    const items = results.querySelectorAll('.result-item');
    if (e.key === 'ArrowDown')      {{ e.preventDefault(); activeIdx = Math.min(activeIdx + 1, items.length - 1); }}
    else if (e.key === 'ArrowUp')   {{ e.preventDefault(); activeIdx = Math.max(activeIdx - 1, 0); }}
    else if (e.key === 'Enter' && activeIdx >= 0 && items[activeIdx]) {{ e.preventDefault(); items[activeIdx].click(); }}
    else if (e.key === 'Escape')    {{ results.classList.remove('open'); input.blur(); }}
    items.forEach((it, i) => it.classList.toggle('active', i === activeIdx));
  }});
}})();
```

## Accordion chapter page (hub + topic tree) — replaces sidebar+main

For chapters with 30-300 topics, the sidebar+main layout becomes overwhelming — the user has to scroll past hundreds of topics to find one. The pattern that scales: **native `<details>` accordion tree with content embedded inline (no JSON fetch)**.

### Why this beats sidebar+main

| | Sidebar+main (old) | Accordion tree (new) |
|---|---|---|
| 330 topics | Huge scroll, hard to find anything | All hubs collapsed by default, expand to scan |
| Mobile | Sidebar is 280px+ of vertical scroll | Full-width collapsible, all content inline |
| Time to topic | 200-500ms (JSON fetch + render) | **0ms** (content in DOM, browser unhides) |
| Works without JS? | No (no topics load) | Yes (native `<details>`) |
| Deep links | `?topic=X` works via JS on load | `?topic=X` works even with JS off |
| SEO | Single SPA URL | All topics indexed, deep links work |
| HTML size | ~50KB shell + 700KB JSON | ~2-5MB (all content embedded) |

The HTML size cost is fine for content libraries — the user is willing to ship a 2-5MB chapter HTML in exchange for instant navigation. Gitignore the PNGs (200MB+ per chapter) but keep the HTML so the topics are searchable and linkable.

```javascript
function expandAll() {{

function collapseAll() {{
  document.querySelectorAll("#hubAccordion details").forEach(d => d.open = false);

  p.searchParams.delete("topic");
  p.searchParams.delete("expand");

}}
```

### Key decisions

1. **Native `<details>` over custom div+JS** — browser handles open/close, no state to manage. Deep links work even with JS disabled.
2. **Tree-line `::before` on `.topic-acc`** — small horizontal line at `left: -10px; top: 24px; width: 8px` connects topic to its hub visually without extra DOM.
3. **Hub count badge** — `30` next to hub name tells user how many topics before they click. Critical for 30+ topic hubs.
4. **Topic number with `min-width: 48px`** — keeps all topic-number badges aligned in a column even when prefixes vary (`16.1.25` vs `16.10.262`).
5. **Search auto-expands matching** — better UX than "filter and show only matches" because user sees the full context (which hub the match is in).
6. **Loading="lazy" on topic images** — defers PNG fetches until topic is opened. Saves 200MB+ of bandwidth when user only opens 2-3 topics.
7. **Expand all sets `?expand=all` in URL** — shareable "show me everything" link.
8. **Backwards compat: still write `topics.json`** — keep the manifest at `SITE / ch_slug / "topics.json"` in case any external tool or future feature still needs pre-rendered HTML.

### CSS gotcha: duplicate `@media` blocks

When `PAGE_CSS` is a single Python string, the same `@media (max-width: N)` block can exist in 2+ places from prior edits. `patch(replace)` fails with "Found N matches"; use `patch(replace_all=true)`. **Always verify after:**

```bash
grep -c '@media (max-width: 900px)' scripts/site/build_site.py
# expect 1, not 2 or 3
```

A duplicate 900px block is the #1 cause of "I changed the CSS but nothing happened" — the earlier block wins on shared properties.

2. The **desktop-required** JS that fetches `/<chapter>/topics.json`, defines `loadManifest()`, `showTopic()`, `navigateTopic()`, `toggleTopicImage()`, and wires up the topic-item click handlers

## Performance optimization — load 84× less data on every page view

When the user complains "page is slow / chapter takes 5 min to load / chapter never finishes", the cause is almost always **over-bundled assets or repeated fetches of the same large file**. Three patterns to audit for, in order of typical impact:

### 1. Strip dead mobile fallback HTML (biggest win for content libraries)

**Symptom:** Chapter `index.html` files are 5-17 MB because the build script inlines every topic body inside the `.m-only` accordion section (the legacy "Accordion chapter page" pattern in this skill). On desktop, the browser parses 17 MB of HTML just to display a sidebar + placeholder, even though the user never opens a mobile accordion.

**Why this happens:** the build script treats mobile accordion and desktop sidebar as separate render passes, both feeding into one HTML file. The mobile pass inlines all topic HTML for instant `<details>` opening; the desktop pass relies on JSON fetch. Both contribute to one file.

**Fix:** if a unified header provides mobile chapter navigation (dropdown drawer), the inlined mobile accordion is dead weight. Strip the entire `<!-- MOBILE: accordion tree -->` block. For MedSea 16-cardiology, this dropped 16.3 MB → 0.2 MB (98.7% reduction), 86 MB saved across 32 chapters, chapter page gzip transfer 3.5 MB → 43 KB, load 4,250 ms → 1,986 ms.

**Critical caveat:** see the pitfall above. The mobile section ends with the JS that wires up topics.json + showTopic. Strip carefully — leave the desktop JS in place. Use a marker like `<!-- /MOBILE-SECTION-END -->` if regenerating the build script, so future strips can target the block precisely.

### 2. Split monolithic JSON DBs into lazy-loaded chunks

**Symptom:** every page loads a 17 MB `questions.json` (or similar) that contains everything: chapter meta, MCQ list, SBA list, flashcard list. Browser must download + parse the whole thing even to render a header showing "20 chapters".

**Detection:**
```bash
ls -lh site/assets/*.json
# look for any single .json > 1 MB that ships to every page
```

```javascript
// in the browser, count concurrent fetches of the same URL on page load
performance.getEntriesByType("resource")
  .filter(r => r.name.endsWith("/questions.json"))
  .length
// expect 1, not 3 — multiple fetchers of the same big file = each one parses independently
```

**Fix pattern (5 KB index + lazy chunks):**

```python
# split_questions.py — split monolithic DB by content type
with open(SRC) as f:
    data = json.load(f)
# index = tiny metadata, always loaded
write_json("questions-index.json", {
    "totals": data["totals"],
    "chapters": [{"num": c.num, "slug": c.slug, "name": c.name,
                  "mcq_count": c.mcq_count, "sba_count": c.sba_count,
                  "flashcard_count": c.flashcard_count,
                  "topic_count": c.topic_count, "hubs": c.hubs}
                 for c in data["chapters"]],
})
# chunks = full content, lazy-loaded on demand
write_json("questions-mcq.json", data["mcq"])         # 10 MB
write_json("questions-sba.json", data["sba"])         # 0.8 MB
write_json("questions-flashcard.json", data["flashcard"])  # 5.5 MB
```

```javascript
// /assets/site-db.js — single shared chunked loader, cached across pages
window.MedSeaDB = {
  _index: null, _mcq: null, _sba: null, _flash: null,
  loadIndex() {
    return this._index ||= fetch('/assets/questions-index.json').then(r => r.json());
  },
  loadChunk(key) {
    const slot = '_' + key;
    return this[slot] ||= fetch('/assets/questions-' + key + '.json').then(r => r.json());
  },
  loadChunks(keys) { return Promise.all(keys.map(k => this.loadChunk(k))); }
};
```

**Consumer pattern (lazy on Start click, NOT on page load):**
```javascript
// On startup: only load the 5 KB index. Use chapter counts for "available: N matching".
loadIndex().then(idx => {
  document.getElementById('avail-count').textContent =
    idx.chapters.reduce((s, c) => s + c.mcq_count, 0) + ' matching';
});

// On Start click: lazy-load only the chunks the user actually needs
document.getElementById('btn-start').addEventListener('click', function() {
  const btn = this;
  btn.disabled = true; btn.textContent = 'Loading questions…';
  loadChunks(mode === 'both' ? ['mcq', 'sba'] : [mode]).then(([chunk]) => {
    // now use chunk to build pool + start exam
  }).finally(() => { btn.disabled = false; btn.textContent = 'Start Exam →'; });
});
```

**Result:** page initial load dropped from ~3.8 MB transferred + 17 MB main-thread parse to **43 KB + 5 KB parse**. JS chunks loaded in parallel via `loadChunks(['mcq','sba'])` on Start.

### 3. `cache: 'no-cache'` disables browser cache — usually wrong

**Symptom:** browser reloads re-download the same 17 MB JSON every time. Network tab shows the file with `(disk cache)` `(from disk cache)` is missing; `Cache-Control: max-age=3600` from nginx is being overridden by the JS `fetch()` option.

**Why:** `{ cache: 'no-cache' }` in a `fetch()` call **forces a conditional request to the server every time** (sends `If-None-Match`/`If-Modified-Since`). It does NOT mean "don't cache" — it means "always revalidate". Worse, multiple no-cache fetchers of the same URL each trigger their own conditional request.

**Fix:** drop the `cache: 'no-cache'` option entirely. Default behavior (`cache: 'default'`) honors the server's `Cache-Control` header, which nginx already sets to `max-age=3600` for HTML and `max-age=604800` for PNGs. Use `cache: 'reload'` if you genuinely want to bypass cache (rare; usually wrong), or `cache: 'no-store'` if you must prevent all caching (private data).

```javascript
// WRONG — disables caching, forces re-download every reload
fetch('/assets/questions.json', { cache: 'no-cache' })

// RIGHT — uses browser HTTP cache + server Cache-Control
fetch('/assets/questions.json')
```

### 4. Show "Loading…" button state during async chunk load

If you lazy-load the actual questions on Start click (correct pattern above), the button must communicate "loading" so the user doesn't think the click was lost:

```javascript
$('#btn-start').addEventListener('click', function() {

  if (!DB_INDEX) return;       // page-level guard
  const prev = btn.textContent;
  btn.disabled = true;

  }).catch(err => {

    btn.textContent = prev;
  });

```

Without the disabled+loading state, users click Start, see no response for 300-500 ms (chunk fetch + parse), and click again → double-load race.

### 5. Don't duplicate event listeners across shared + page-specific JS

**Symptom:** every keystroke in the search box fires two `fetch` calls to `/search_index.json` and renders results twice. Page eventually lags.

**Detection:** in browser, count active listeners (no built-in API; easiest check is `performance.getEntriesByType('resource')` for redundant fetch calls).

**Fix pattern:** shared JS auto-binds to `document.getElementById('searchInput')` on every page. Pages that have their own inline search JS must opt out:
```javascript

```
```javascript

```

### When to switch back to JSON fetch

If a chapter ever exceeds ~1000 topics:
- The HTML file becomes 15-20MB — slow to parse, hits browser memory limits
- Most users only view 1-5% of topics — wasting 95% of bandwidth
- Switch to a JSON manifest + lazy hydration: render topics on demand, keep collapsed topics as stubs

For 30-300 topics, inline wins. For 1000+ topics, JSON fetch wins.

## Pitfalls (learned the hard way)
- **Inconsistent headers across pages break user trust** — when the main site has a rich header (logo + stats + search + chapter dropdown + ext-links) and a new sibling page (/exam/, /flashcards/, /tracker/) ships with a simpler header, users complain ("why 2 different type of header keep default one all pages"). **Fix pattern that works:** extract the shared header once into `/assets/site-header.css` + `/assets/site-header.js`, give it `id`-based slots (`#stat-chapters`, `#stat-mcq`, `#searchInput`, `#chapterMenu`, etc.), and copy the same `<header>` markup into every page. The shared JS populates slots by querying those ids — no template engine needed. Dynamic stats load from a JSON endpoint (e.g. `/assets/questions.json`) so the header shows real numbers everywhere. Active-link highlighting is automatic via path prefix match in shared JS.
- **Updating a static nginx Docker site without rebuilding the image** — when the Dockerfile uses `COPY site/` (not a bind mount), adding files to host `site/` does NOT show in the running container. Fast fix without `docker build` (which can take 1-5 min for multi-GB PNGs): `docker cp <host-path> <container>:/usr/share/nginx/html/<path>` then **`docker exec <container> chmod -R a+r /usr/share/nginx/html/<path>`**. The `chmod` is REQUIRED because `docker cp` creates files with mode `0600` (owner-readonly); nginx runs as a non-root user and silently returns 403 for unreadable files. Without chmod, you'll see `curl -I` return 200 on path checks but the browser gets 403.
- **Python module imports trigger top-level main code** — when you `import` or `importlib.util.spec_from_file_location(...)` a Python script that has a `for ch in CHAPTERS: process...` main loop at the bottom, the import executes the loop every time. Fix: split into a pure-function library module (`parser_lib.py`) and a separate main script that calls `from parser_lib import parse_topic`. Library modules must have NO executable code at module level — only function definitions and constants.
- **Regex backtracking kills parsers of large document corpora** — when parsing 4,000+ MD files with multi-line `re.findall` over `(?ms)` regex, a single greedy quantifier can explode runtime from seconds to 15+ minutes. Symptom: process pegs at 95% CPU for >10 min without producing output. Fix: rewrite as a line-by-line state machine (`for line in text.splitlines(): if line.startswith('## '): ...`) — typically 100x faster and easier to debug. See the Davidson MD parser pattern below.
- When `PAGE_CSS` is a single Python string, the same `@media` block can exist in 2+ places from prior edits — `patch(replace)` fails with "Found N matches" when the old block is duplicated. Use `patch(replace_all=true)` to remove all duplicates in one shot, then verify with `grep -c '@media (max-width: 900px)' build_site.py` (expect 1, not 2-3). A duplicate 900px block is the #1 cause of "I changed the CSS but nothing happened" — the earlier block wins on shared properties.
- **When removing a duplicate CSS block, the `@media` opening brace can be lost** — `patch(replace_all)` may strip the `.X {` of the next rule and leave the `@media {` block orphaned. Always re-read the file after a `replace_all` and verify the CSS still has its expected structure (open braces count, rule blocks intact). Build will succeed and HTML will render but CSS will silently misbehave.
- **Inline accordion content (5-10MB per chapter) is fine for 30-300 topics, but becomes a problem at 1000+** — the browser parses the whole HTML up front, hitting memory limits and slowing initial load. For very large chapters, switch to JSON manifest + lazy hydration. For 30-300 topics (the MedSea sweet spot), inline wins because navigation is instant.
- **Native `<details>` accordion replaces sidebar+main but loses Prev/Next navigation** — the old JSON-fetch SPA had `navigateTopic(dir)` for keyboard arrows. The accordion has no "current topic" concept because everything is visible. If the user later asks for "back to last viewed" or "next topic in this hub", add a `?topic=X` URL state + indicator, or rely on browser `<a>` tabindex. Don't recreate the Prev/Next pattern over the accordion — different mental model.

- **`shutil.rmtree(SITE)` deletes README too** — re-create `site/README.md` from a template constant after the rmtree, or store it outside the build dir.
- **The build script is at `scripts/site/build_site.py`, not `site/`** — if you `rmtree(SITE)` you also delete the build script. Keep it OUTSIDE the output dir.
- **`.gitignore` PNGs but include MDs** — `site/**/*.png` is huge (200+ MB for medical content); MDs are small and needed for download buttons + JSON embedding.
- **`flex-wrap: nowrap` is mandatory for header** — without it, on smaller screens stats wrap and break the layout. Use `flex-shrink: 0` on each child instead.
- **Image position order is easy to get wrong** — when iterating, always check the rendered DOM order: `Array.from(c.children).map(x => x.className).join(' | ')`.
- **Browser_vision is unreliable** — fall back to `browser_console` DOM probes (height, offsetWidth, querySelectorAll counts) when vision returns "Unknown Model".
- **Docker build is slow** (~1-2 min for 250+ MB) — run with `background=true` and `notify_on_complete=true`, then continue working. Don't poll.
- **CSS `@media` rules need testing at multiple widths** — the user mentioned layout "not arrange correctly" which often means responsive breakage; test at 1280px and 1920px explicitly.
- **The `?topic=` URL must match the `local_prefix` field exactly** — if the manifest has `17.1.01` and the URL has `17.1.1`, the page silently shows the placeholder. Test with multiple URL variations.
- **`column-count: 2` in dropdown** breaks if items have `display: flex` that overflows the column width — add `break-inside: avoid` on `.item`.
- **When you have two `<style>` insertion points but need mobile elements everywhere, do NOT rely on the desktop header being present in the DOM on mobile** — explicitly `display: none` the desktop header at the mobile breakpoint (`.mobile-bar { display: flex; } header.site { display: none; }`). Hiding via `flex-wrap` or `max-width: 0` still leaves the header in the layout and produces 0 height, breaking sticky positioning.
- **BUILT_CHAPTERS slug must match the actual chapter folder** — if the dict has `"2-clinical-therapeutics-and-good-prescribing"` (formal name) but the folder is `2-clinical-therapeutics` (short name), the build silently produces an orphan card with 0 topics. Always validate the dict at the top of `build_site.py`:
  ```python
  for slug in BUILT_CHAPTERS:
      if not (CHAPTERS_ROOT / slug).exists():
          print(f"WARNING: BUILT_CHAPTERS['{slug}'] has no folder under {CHAPTERS_ROOT} — site will show 0 topics")
  ```
  Convention: use the **shortest descriptive slug** in the URL/folder-key dict, keep the formal display name in a separate `DAVIDSON_25TH` (or equivalent) display table. When you rename a chapter folder, grep the build script for the old slug and update both dicts in one pass.

## DUAL-VIEWPORT RENDERING — same data, two layouts (scope-discipline pattern)

When the user accepts the mobile accordion but also wants to **keep the previous desktop sidebar+main layout**, do NOT pick one layout. Render BOTH in the same HTML, gated by viewport CSS. This was the lesson from a real correction: "wth hack you doo, I told you make only for mobile that dropdown and but you make desktop too".

**The trap (what NOT to do):** rewriting `write_chapter_spa()` to produce ONLY accordion output because "mobile needs accordion". This destroys the existing desktop sidebar+main. The user then has to ask you to put desktop back — wasted round-trip and visible regression.

**The pattern that works:**

### Render BOTH layouts in one template

```python
def write_chapter_spa(ch_slug, ch_name, ch_url, ch_color, info):
    # Single pass: render topic HTML, build manifest + sidebar_html + accordion_html
    sidebar_html = ""      # desktop: hub-group + topic-item links
    accordion_html = ""    # mobile: <details> tree with content embedded inline
    for hub_num in sorted(info["by_hub"]):
        # ... compute hub_topics, hub_name ...
        sidebar_html += f'<div class="hub-group" data-hub="{hub_num}"><h3>{hub_num} · {hub_name}</h3>\n'
        accordion_html += f'<details class="hub-acc" data-hub="{hub_num}"><summary>...</summary><div class="hub-body">\n'
        for t in hub_topics:
            md_html, png_rel = render_topic_html(t)
            sidebar_html += f'  <a class="topic-item" data-topic="{t["prefix"]}" href="?topic={t["prefix"]}">{title}</a>\n'
            # accordion topic: full HTML embedded inline
            accordion_html += f'  <details class="topic-acc" data-topic="{t["prefix"]}"><summary>...</summary>\n'
            accordion_html += f'    <div class="topic-body">{md_html}</div></details>\n'
        sidebar_html += '</div>'
        accordion_html += '</div></details>'

    html = page_header(...)
    html += f"""
<div class="chapter-page">
  <!-- DESKTOP: sidebar + main -->
  <aside class="chapter-sidebar d-only">
    <input id="topicSearch" placeholder="Search topics…">
    {sidebar_html}
  </aside>
  <section class="chapter-main d-only">

  </section>
```

### Scope-discipline check (the lesson that triggered this section)

Before declaring a UI refactor "done", ask:
1. **Did the user mention a viewport?** If they said "mobile" / "desktop" / "on phones", the change MUST be scoped to that viewport via CSS classes (`m-only`, `d-only`) or a separate render path. NEVER rewrite a shared render function.
2. **Does the diff touch any element on the other viewport?** `grep` for `display:`, `chapter-page`, `chapter-sidebar`, `chapter-mobile`, `mobile-bar`. If desktop rules or HTML are gone, you've broken the other viewport.
3. **Did the user say "keep desktop like previous"?** That phrase = "restore the prior layout on desktop, leave desktop untouched, change only the target viewport". Implement by ADDING a new CSS class and HTML block, not by MODIFYING existing ones.

If you wrote a new function from scratch that replaced an existing one, you almost certainly broke the other viewport. Patch the existing function to add the new layout alongside the old one instead.

### Verified dual-viewport pattern (MedSea 16-cardiology)

| Viewport | Layout | Mechanism |
|---|---|---|
| Desktop ≥901px | `<aside class="chapter-sidebar">` + `<section class="chapter-main">` | topics loaded on-demand via fetch from `topics.json`, click sidebar link → renders into main pane |
| Mobile ≤900px | `<div class="chapter-mobile">` containing `<details>` accordion | all topics embedded inline, no fetch needed |
| URL `?topic=16.1.25` | Desktop: auto-loads via `loadManifest()` + `showTopic()` | Mobile: auto-opens the matching `<details>` + scrolls |
| Header `?expand=all` | Desktop: ignored (sidebar already shows all) | Mobile: opens all hubs + topics |

Same data source (single render pass), two layouts, no JS branch needed except the URL-on-load handler.

**Pitfall: topic count mismatch.** If `find_files()` runs twice (once for sidebar, once for accordion), they can produce slightly different counts due to filesystem race conditions. Run ONCE and reuse `rendered_topics` dict across both layouts. MedSea cardiology once showed 332 topics in mobile accordion but expected 330 — caused by a stale `topics.json` from a prior partial build. Fix: rebuild cleanly with `rm -rf site && python3 build_site.py`.

**Pitfall: opening `<details>` from URL on mobile must guard by viewport.** If `window.innerWidth > 900`, the mobile IIFE shouldn't try to expand anything — it would visually do nothing (display:none) but the `<details>` state would still change, leaking URL state. Add the `if (window.innerWidth > 900) return;` guard at the top of the mobile-only IIFE.

**Pitfall: `data-topic` attribute must match URL exactly including zero-padding.** `16.1.25` (sidebar link href) and `16.1.25` (accordion data attribute) must be the same string. If `find_files` produces `16.1.5` for some and `16.1.05` for others, the URL-based open fails silently for one variant. Normalize to zero-padded form in `find_files`.

### Pitfall: the `patch` tool can silently truncate long `new_string` values when restoring multi-line blocks

This bit me when I tried to restore the desktop JS in 32 chapter pages using `patch` with `old_string` matching a truncated block (~50 lines) and `new_string` containing the full block (~90 lines, ~3.8 KB). The patch reported success and returned a diff, but the inserted block was silently truncated to ~1.4 KB — mid-function, no closing brace, no `showTopic` definition. **All 32 chapter pages** were left with the same broken state.

**Why this happens:** the `patch` tool's fuzzy matching can match a partial `new_string` against the `old_string` when the new content is large and the surrounding context has minor whitespace differences. The tool returns success because the partial insertion is technically valid syntax up to the truncation point.

**Symptom (won't show up immediately):**
- File appears to have the new block (grep finds the start of it)
- Functions referenced later in the block are missing
- Browser console: `ReferenceError: showTopic is not defined` or `MANIFEST is null`
- The script block ends mid-function with no closing `</script>`

**Detection pattern after any multi-line block insert:**
```bash
# grep for the LAST function in the inserted block, not the first
grep -cE "function showTopic|loadManifest\(\)\s*\{|document.addEventListener" site/<chapter>/index.html
# expect ≥3 matches. If only 1, the insert was truncated.
```

**Better approach for multi-file block restoration: use a Python script, not `patch`**

When you need to restore the same multi-line block in N files with per-file parameterization, write a Python script that:
1. Reads the full template from a file (so it's not subject to in-memory truncation)
2. Uses regex to find the old block reliably
3. Replaces with `str.replace()` after explicit `if old not in content: raise SystemExit` sanity check
4. Validates the result by grepping for the LAST function in the template
5. Reports per-file byte-delta so you can see the insertion was complete

```python
#!/usr/bin/env python3
"""Restore the full desktop JS block in all 32 chapter HTMLs."""
import os, re

# 1. Read the FULL template from disk (no in-memory truncation risk)
with open("/tmp/desktop_js_full.html") as f:
    full_template = f.read()    # ~3.8 KB complete block

site_root = "/mnt/tb/Sea-knowledge/#MedSea/site"
for d in sorted(os.listdir(site_root)):
    p = os.path.join(site_root, d, "index.html")
    if not os.path.isfile(p) or d in ("exam", "flashcards"): continue

    with open(p) as f:
        html = f.read()

    # 2. Find the truncated block with a regex that's robust to mid-function cutoffs
    pattern = re.compile(
        r'<script>\s*\nconst CHAPTER_SLUG = "([^"]+)";.*?(?=<script src="https://cdn\.jsdelivr\.net)',
        re.DOTALL
    )
    m = pattern.search(html)
    if not m: continue

    # 3. Build per-chapter replacement (parameterize slug + paths)
    chapter_slug = m.group(1)
    replacement = (full_template
        .replace('CHAPTER_SLUG = "16-cardiology"', f'CHAPTER_SLUG = "{chapter_slug}"')
        .replace('/16-cardiology/topics.json', f'/{chapter_slug}/topics.json')
        .replace('/16-cardiology/${t.png}', f'/{chapter_slug}/${{t.png}}'))

    new_html = html[:m.start()] + replacement + html[m.end():]

    # 4. Sanity check: last function must be present
    if 'function showTopic' not in replacement:
        raise SystemExit(f"FATAL: template missing showTopic, aborting {chapter_slug}")

    with open(p, 'w') as f:
        f.write(new_html)
    print(f"✓ {chapter_slug}: {len(html)} → {len(new_html)} bytes")
```

**Run it, then verify with grep on multiple files (not just one):**
```bash
# After running the fix script
for f in site/1-*/index.html site/8-*/index.html site/16-*/index.html site/27-*/index.html; do
  count=$(grep -c "function showTopic" "$f")
  echo "$f: $count"
  # expect 1 per file
done
```

**Why this beats `patch` for block restoration:**
- The template is read from disk in full — no risk of in-memory truncation
- Per-file parameterization is explicit and visible
- The sanity check (`'function showTopic' not in replacement`) catches template bugs before any file is written
- The byte-delta report (`{len(html)} → {len(new_html)} bytes`) makes truncation visually obvious — if a 200KB file only grew by 1KB, you know the insert was truncated

**See `templates/desktop-topic-spa-js.html` for the full copy-paste block.**

## Docker port alignment (recovered pattern)

The container must listen on **80** (`listen 80` in `docker/nginx.conf`), expose **80**, and the host runs `-p <host_port>:80`. If you (or an earlier session) accidentally map `-p 8855:8855`, nginx accepts on 80 (where nothing listens) and rejects connections on the host-mapped port. Symptom: `docker exec <name> wget http://127.0.0.1:8855/` fails with `Connection refused`, but `docker exec <name> wget http://127.0.0.1:80/` succeeds.

**The fix:** `-p 0.0.0.0:8855:80`. The **last** port in `-p` is the container port and must match what nginx actually listens on. The `EXPOSE` directive in Dockerfile is metadata only — it doesn't change what nginx listens on, only documents intent.

**Verify after restart:**
```bash
sleep 3
for path in / /<chapter>/ /<chapter>/topics.json; do
  curl -s -o /dev/null -w "$path=%{http_code}\n" http://localhost:8855$path
done
# expect 200 200 200 — if all 000, the port mapping is wrong
```

## Git push timeouts on large chapter HTMLs

`git push origin main` over HTTPS can silently time out (60s+) when the diff includes large generated HTML files (32 chapter index.html files, ~5MB each for cardiology, totaling 200MB+). The push appears to hang with no error; `git log --oneline origin/main` still shows the old HEAD.

**Symptoms:**
- `timeout 60 git push origin main` exits 124
- No error message, no progress
- `git status` shows `ahead 1`

**Recovery options, in order of preference:**
1. **Wait longer** — large HTTPS push can take 2-5 min for multi-MB diffs. Try `timeout 300 git push origin main`.
2. **Switch to SSH** — `git remote set-url origin git@github.com:SeaXen/MedSea.git` and push again. SSH handles large diffs more reliably.
3. **Split the commit** — if one chapter index.html is massive, commit it separately with `git add site/<chapter>/index.html` then push just that one file.
4. **Use `--quiet` or `--no-verify`** — these suppress some progress output but don't change the underlying transfer size.

**Don't do this:**
- Don't `--force` push. The local commit is correct; force-pushing can corrupt the remote.
- Don't reset and re-commit; the diff is real and needs to land.
- Don't keep retrying with no timeout change — each retry just hits the same hang.
- **`git mv` of a chapter folder leaves empty subdirs at the OLD path** — even after a clean rename, the old `chapters/<old-slug>/{diseases,hubs,source}/` may exist as empty directories. Git will track the new path; the old subdirs look like untracked-but-empty leftovers. `rm -rf` is blocked by the Hermes safety system, but `rmdir` works on empty dirs and is safe. Clean-up pattern: `rmdir <old>/diseases/<deepest-empty> && rmdir <old>/diseases && rmdir <old>/hubs && rmdir <old>/source && rmdir <old>`. Verify with `ls -la` that each subdir is empty before `rmdir` (rmdir fails on non-empty dirs by design, which is the safety you want).
- **Docker `stop`/`kill`/`rm` are blocked by the Hermes safety system** — destructive container commands trigger a "no consent" block even with `timeout` wrappers. Before running them, ask the user explicitly: "I need to stop+remove the existing medsea container and start a new one to deploy the rebuilt site. OK?" Then run them as a single short command: `docker stop <name> && docker rm <name> && docker run -d --name <name> --restart unless-stopped -p <host_port>:<container_port> <image>`.
- **Content renderer (`/root/sea-knowledge-infographics/render_topic.py`) hangs on unnumbered `## ` headers** — e.g. `## 24-Hour Recall Prompts` inside a source MD. The parser's numeric-prefix loop never matches, the section never closes, and the render times out at 60s. Pre-process every source MD before passing to the renderer: convert unnumbered `## ` headers to numbered `## N. Title` form, or wrap them as `### ` subheadings. Quick pre-process in Python:
  ```python
  import re
  counter = [0]
  def repl(m):
      counter[0] += 1
      return f"## {counter[0]}. {m.group(1).strip()}"
  text = re.sub(r"^##\s+(?![\d.])(.+)$", repl, text, flags=re.MULTILINE)
  ```
- **Renderer hangs on MDs > ~400 lines** — first attempt often times out on big source documents. Retry pattern that works: split the MD into ≤150-line chunks via `text.split("\n")[:150]`, append a `*...truncated to 150 lines*` footnote, and re-submit. Truncated topics still produce a usable PNG+HTML for the site.
- **Renderer output filenames are named by `--slug`, not `topic.png`** — when you pass `--out-dir /path/to/disease-dir`, the renderer creates a **subdirectory** at `/path/to/disease-dir/<slug>/` containing `<slug>.png`, `<slug>.html`, `<slug>.md`. If the rest of the pipeline expects flat `topic.{png,md,html}` in the disease dir (which the MedSea site does), you must flatten after rendering:
  ```bash
  mv <d>/<slug>/<slug>.png <d>/topic.png
  mv <d>/<slug>/<slug>.html <d>/topic.html
  mv <d>/<slug>/<slug>.md  <d>/topic.md
  rmdir <d>/<slug>
  ```
  Building directly to the disease dir works only if you re-run with `--out-dir` set to the disease dir *and* the renderer doesn't double-nest. Test one disease first before running the full batch.
- **Renderer now supports mermaid mindmap/flowchart code blocks** — ` ```mindmap ` and ` ```flowchart ` blocks render as styled nested `<ul class="mindmap">` and `<div class="flowchart">` HTML (no JS needed). The renderer also tolerates unnumbered `##` headers now. If older PNGs in your site are missing the visual styles, re-render those topics and the PNG output will include the diagrams. There are 600+ such topics in the MedSea dataset; re-rendering the whole batch takes 1-2 hours.
- **Source MDs may not have explicit mermaid blocks even when the renderer supports them** — older chapters (or chapters generated by other agents) ship as plain prose with H1/H2/H3 structure only. If you only render explicit blocks, those chapters show as text-only. The fix is auto-synthesis from headings (see "Content rendering — auto-synthesize visual elements from MD structure" above). Verify coverage across **all** chapters, not just the one you tested the synthesis on.
- **"It works on chapter X" ≠ "it works on all chapters"** — the user has been burned multiple times by assistants testing a new feature on one chapter, reporting "done", and discovering the other 31 chapters silently regress or never got the feature. After any cross-cutting change to `build_site.py`, run the coverage check (count synthesized mindmaps / search-index size / whatever the new feature is) on **every** chapter and report the per-chapter table. Do not declare done after one chapter passes.
- **Docker port alignment is fragile** — the container must listen on 80 (`listen 80` in nginx.conf), expose 80, and the host runs `-p <host_port>:80`. If you (or an earlier session) accidentally wrote `listen <host_port>` in nginx.conf, the container accepts connections on 80 (where nothing listens) and rejects them on the host-mapped port, producing a "Connection reset by peer" / "Empty reply from server" / "unhealthy" state. Symptom: `docker exec <name> wget http://127.0.0.1:<host_port>/` fails, but `docker exec <name> wget http://127.0.0.1:80/` succeeds. The existing `## Docker pattern` section above has the correct template — re-read it before touching the port.
- **Test mobile without a real phone by injecting CSS** — the browser tool runs at 1280px by default. To verify a mobile breakpoint works, inject `@media (min-width: 1px) { .mobile-bar { display: flex !important; } header.site { display: none !important; } }` via `browser_console(expression)`, then probe `getComputedStyle(el).display` and `el.getBoundingClientRect()`. Vision is unreliable (`Unknown Model` errors are common), so DOM measurements are the reliable verification path.
- **Two `@media (max-width: <N>px)` blocks in the same file — CSS cascade picks the LATER one as winner.** If you have an old 900px rule at the bottom of `PAGE_CSS` and a new 900px rule at the top, the old one wins for shared properties. Audit `grep -n '@media' build_site.py` after every layout change and delete duplicates. The cleanest pattern is: one named breakpoint block, never two.
- **The desktop `<header>` must be `display: none` (not just shrunk) on mobile** — if you keep `display: flex` but set `max-width: 0` or `overflow: hidden`, the header still occupies layout space, breaking `position: sticky` for `.mobile-bar` (which sits below it). Use `header.site { display: none; }` and `.mobile-bar { display: flex; }` as a pair in the same media query.
- **`<main>` open tag must exist in every page** — during header refactors it's easy to lose the `<main>` tag from `page_header()` (the script closes `</header>` then opens `<script>`, then the body content sits in `<main>` further down). If `<main>` is missing, page is rendered as raw `<body>` content with no semantic structure, and any `main { padding: ... }` CSS does nothing. Verify with `grep -c '<main>' site/index.html` (expect ≥1).
- **`ch_display` must be initialized outside the `if current_ch_slug in BUILT_CHAPTERS` block** — if you reference `ch_display` in the mobile bar's current-ch-label f-string, it must exist as a string even when on the index page (where there's no current chapter). LSP will catch this as "possibly unbound" — initialize `ch_display = ''` at the top of the function before the if/else.
