# Encrypted HLS Download from LMS / Course Platforms

When yt-dlp, N_m3u8DL-RE, and IDM all fail on a paid course video, the cause is almost always: **the AES-128 key server requires authenticated headers that download tools don't generate**. The fix is to **use a headless browser to log in, then intercept the key-server response**, then download + decrypt segments yourself with the captured key.

## When to use

Trigger this skill when ALL of the following are true:
- User has legitimate login access to a video (paid course, LMS, internal portal)
- yt-dlp returns `Unsupported URL`, `403`, or decrypts but produces silent / corrupted output
- IDM shows "IDM cannot download this protected stream for legal reasons"
- The platform's HLS player loads in a browser and plays the video
- The .m3u8 playlist contains `EXT-X-KEY:METHOD=AES-128,URI="..."` pointing to a kms / keys endpoint

**Do NOT use** for:
- Public YouTube / Vimeo / Dailymotion (use `media:youtube-content` or plain yt-dlp)
- Widevine / PlayReady / FairPlay DRM (legal + technical dead end — only authorized players decrypt)
- Netflix / Prime / Disney+ (same)
- Content the user does not have an account for

## Diagnostic: confirm the pattern before attempting the full pipeline

```bash
# 1. Fetch the m3u8 directly with browser-like headers
curl -sS -H "Referer: https://player.vidinfra.com/" \
        -H "User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/149.0.0.0 Safari/537.36" \
        "https://<CDN>/<stream_id>/playlist.m3u8"
# → if you get the master playlist (with 720p/media.m3u8 etc.), CDN is open

# 2. Try the key server with the same headers
curl -sS -H "Referer: https://player.vidinfra.com/" \
        -H "User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/149.0.0.0 Safari/537.36" \
        "https://kms.vidinfra.com/v1/keys?content_id=<stream_id>"
# → "missing authentication headers" or 401/403 = need browser-based key capture
# → binary 16 bytes = key is public, yt-dlp should work — your problem is elsewhere
```

If step 1 succeeds but step 2 fails with auth error → **this skill applies**.

## Strategy ladder (try in order)

1. **yt-dlp + browser cookies** — `yt-dlp --cookies-from-browser brave "PAGE_URL"`. Works when the auth is just cookies. Fast to try, often fails because the key server needs more than cookies.
2. **N_m3u8DL-RE with manual cookies** — Windows tool, doesn't extract browser cookies natively. User has to export cookies manually. Often fails for the same reason.
3. **Playwright headless + key interception + parallel decrypt** — the heavy hammer. Works when auth requires signed headers generated by the player JS. **This is the technique that worked for Synapse Medical Academy on a Bangladeshi medical course platform.**
4. **Screen record with OBS / ffmpeg + virtual display** — last resort when the player uses true DRM or generates a per-session signature that can't be replayed. Loses quality, but always works.

## Strategy 3: Playwright key-capture + parallel decrypt (full recipe)

### Phase 1 — Capture the AES-128 key

```python
import asyncio
from playwright.async_api import async_playwright

LMS_URL   = "https://<lms>/<path-to-lecture-page>"   # page where user clicks the lecture tile
USERNAME  = "..."   # ask the user; do not invent
PASSWORD  = "..."   # ask the user; do not invent

async def capture_key():
    async with async_playwright() as p:
        browser = await p.chromium.launch(headless=True, args=["--no-sandbox"])
        context = await browser.new_context()
        page = await context.new_page()

        kms_body = {"data": None}
        async def on_response(r):
            if "kms" in r.url and "/v1/keys" in r.url:
                try: kms_body["data"] = await r.body()
                except: pass
        page.on("response", lambda r: asyncio.create_task(on_response(r)))

        # Login flow
        await page.goto(LMS_URL, wait_until="domcontentloaded")
        if "/login" in page.url:
            await page.get_by_placeholder("Enter mobile number").fill(USERNAME)
            await page.get_by_placeholder("Type your password").fill(PASSWORD)
            await page.get_by_role("button", name="Sign In").click()
            await page.wait_for_url(lambda u: "/login" not in u)

        # Open the lecture page
        await page.goto(LMS_URL, wait_until="domcontentloaded")
        # The user said "you need to click on video after go to lecture page"
        await page.locator('text="<video-title>"').first.click()

        # Wait for key
        for _ in range(30):
            await page.wait_for_timeout(1000)
            if kms_body["data"]:
                break
        return kms_body["data"]
```

**Why this works:** the key server (`kms.vidinfra.com/v1/keys?content_id=...`) requires headers like `x-auth-nonce`, `x-auth-timestamp`, `x-auth-signature` (HMAC-SHA256 over content_id + nonce + timestamp). The player JS computes these per request. Instead of reverse-engineering the JS, we let the browser do it and intercept the response.

### Phase 2 — Fetch the segment list

```python
import re, urllib.request
HEADERS = {
    "Referer": "https://player.vidinfra.com/",   # or whatever the player uses
    "User-Agent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/149.0.0.0 Safari/537.36",
}
url = f"https://<CDN>/<stream_id>/720p/media.m3u8"
with urllib.request.urlopen(urllib.request.Request(url, headers=HEADERS)) as r:
    playlist = r.read().decode()
segments = [int(s) for s in re.findall(r"^segment-(\d+)\.ts\s*$", playlist, re.MULTILINE)]
```

### Phase 3 — Parallel download + AES-128-CBC decrypt + concat

```python
from concurrent.futures import ThreadPoolExecutor, as_completed
from Crypto.Cipher import AES

key = open("/tmp/key.bin", "rb").read()   # 16 bytes

def fetch(seg_id):
    u = f"https://<CDN>/<stream_id>/720p/segment-{seg_id}.ts"
    with urllib.request.urlopen(urllib.request.Request(u, headers=HEADERS)) as r:
        return seg_id, r.read()

enc = {}
with ThreadPoolExecutor(max_workers=24) as pool:
    futs = {pool.submit(fetch, s): s for s in segments}
    for fut in as_completed(futs):
        sid, data = fut.result()
        enc[sid] = data

with open("/root/<output>.mp4", "wb") as out:
    for sid in sorted(enc.keys()):
        # HLS default IV = media sequence number as 16-byte big-endian
        iv = sid.to_bytes(16, "big")
        cipher = AES.new(key, AES.MODE_CBC, iv)
        decrypted = cipher.decrypt(enc[sid])
        # PKCS7 padding only on the last segment
        if sid == segments[-1]:
            pad = decrypted[-1]
            if 1 <= pad <= 16 and decrypted[-pad:] == bytes([pad]) * pad:
                decrypted = decrypted[:-pad]
        out.write(decrypted)
```

### Phase 4 — Remux MPEG-TS to true MP4 (auto)

The decrypted output is MPEG-TS (the HLS container). Most players handle `.ts` with `.mp4` extension fine, but some Android gallery apps and strict "MP4 only" hardware players refuse. Always remux to a true MP4 container as the last step — it's a stream copy, takes seconds, no quality loss, and saves ~10-15% size by stripping TS null-packet padding.

```python
import subprocess
from pathlib import Path

ts_path = "/root/output.ts"          # whatever the concat wrote
tmp = Path(ts_path).with_suffix(".remux.mp4")
subprocess.run([
    "ffmpeg", "-hide_banner", "-loglevel", "error", "-y",
    "-i", ts_path, "-c", "copy", "-movflags", "+faststart", str(tmp),
], check=True)
Path(ts_path).unlink()
tmp.rename(Path(ts_path).with_suffix(".mp4"))
```

The script in `scripts/hls_decrypt.py` runs this as Phase 4 by default — the final output is a true MP4, not a relabeled TS.

### Phase 5 — Verify

```bash
ffprobe -v error -show_format -show_streams output.mp4 | head
# Expect: h264 1280x720, aac 48kHz, duration ~= the source video's duration
# Format: mov,mp4,m4a (not mpegts — that's the whole point of the remux)
```

## HLS spec details that bite you

| Detail | Correct handling |
|---|---|
| **IV** | If `EXT-X-KEY` has no `IV=` attribute, IV = 16-byte big-endian media sequence number. Don't assume zero IV — only segment 0 uses zero. |
| **PKCS7 padding** | Last segment only. Last byte is pad length, last N bytes must equal `bytes([N])*N`. Strip before writing the final frame. |
| **Playlist line endings** | Playlists are CRLF (`\r\n`). Regex like `^segment-(\d+)\.ts$` with `re.MULTILINE` finds **zero matches** because `$` matches before `\n`, not before `\r\n`. Use `^segment-(\d+)\.ts\s*$` (note `\s*`). |
| **Manifest vs media playlist** | The `playlist.m3u8` is a master listing of quality variants. The actual segments are in `<quality>/media.m3u8`. Fetch the media playlist to get segment list. |
| **AES-128 vs SAMPLE-AES** | `METHOD=AES-128` is per-segment CBC — decrypt with the script above. `METHOD=SAMPLE-AES` is per-sample encryption (often Widevine/PlayReady) — not solvable this way. |
| **Container** | HLS segments are MPEG-TS. Output will be `.ts`/`.mp4` with `format_name=mpegts`. Plays fine in VLC, mpv, browsers, Android, iOS. Some strict "MP4 only" players want remux: `ffmpeg -i input.ts -c copy output.mp4`. |

## Pitfalls

- **/tmp is tmpfs on this host** — venvs created at `/tmp/...` get wiped between terminal calls. Install persistent venvs at `/root/.venvs/<name>` (or wherever survives across calls). Confirmed with `mount | grep /tmp` returning `tmpfs`.
- **`Path.with_suffix()` only replaces the LAST suffix.** `Path("foo.mp4.ts.tmp").with_suffix(".remux.mp4")` produces `foo.mp4.ts.remux.mp4`, **not** `foo.mp4.remux.mp4`. If you use a multi-dot intermediate filename (e.g. `<output>.mp4.ts.tmp`), explicitly build the output path with `Path(out_name).stem + ".remux.mp4"` or pass an explicit suffix. The script in this skill uses a single `.ts` intermediate to avoid this trap.
- **`vision_analyze` / image understanding is unavailable** on this model right now. If the user pastes an error screenshot, run `tesseract /path/to/img /tmp/ocr_out -l eng` to OCR it.
- **`document.cookie` is empty for many LMSes** — Synapse stores its session in `localStorage.sessionId` (an express-session token used as a `Bearer` auth header on the API), not as a real cookie. So `--cookies-from-browser` returns nothing useful. Playwright `context.cookies()` is also empty for these platforms. Don't waste time fishing for cookies that don't exist.
- **IDM doesn't send `Referer` / `User-Agent` correctly** for cross-origin key requests — even with the right cookies, the key server's CORS / Referer check fails. That's why IDM shows "IDM cannot download this protected stream" even when the user is logged in. yt-dlp with `--add-header` works better, but for HMAC-signed key requests you need the player JS itself to generate the signature — which means a real browser.
- **Headless Chromium user-agent is distinctive** (`HeadlessChrome/...`). Some servers refuse. Fix: pass a real desktop UA into the `new_context(user_agent=...)` call. Confirmed: passing Chrome 149 Win11 UA worked on `kms.vidinfra.com`.
- **The "click the video tile" step is required** — for Synapse, the lecture page lists tiles but doesn't auto-play. After login + navigation, you must click the video title element to open the player iframe, which then fires the key request.
- **Chapters often have multiple videos, not one** — a "lecture page" in Synapse (and similar LMSes) shows a grid of video tiles (e.g. 2 cards: "Gastroenterology - 01.mp4" and "Orientation December-26"). `page.locator('text="..."')` works when titles are unique, but breaks if titles repeat or contain special characters. More robust: enumerate the tiles, list their titles, click by index. The video title you pass to `capture_key()` is just for matching — the click must actually open the player.
- **Don't `await page.evaluate("iframe.contentDocument.querySelector('video').play()")` from the parent** — cross-origin frame access is blocked and throws `SecurityError`. Just `await page.wait_for_timeout(8000)` after clicking the tile; the player auto-starts and the key request fires.
- **The lecture-page `stream_id` changes per video** — the UUID in `player.vidinfra.com/stream/{content_id}/default/{stream_id}` is per-video, not per-chapter. Capturing it for one video does not let you download sibling videos on the same page. Each video needs its own capture run. Or, if the platform exposes an API that returns all `stream_id`s for a chapter (e.g. `GET /api/lecture/{id}` in Synapse returns `videoContents[]`), iterate them.
- **Don't label a `.ts` file as `.mp4` and call it done** — players usually handle it but some (older Android, some smart-TVs) refuse. The remux is a 5-second stream copy, never skip it. After remux, **verify with ffprobe** that `format_name=mov,mp4,m4a` (not `mpegts`) and **report the container format explicitly** in the completion message. The user notices when a `.mp4` is actually `.ts` — save the round-trip.
- **Don't trust marketing copy for content count** — Synapse's brochure says "50 Classes" for the course, but the actual `GET /api/lecture/{id}` for the active chapter returned only 2 `videoContents` and 0 `fileContents`. Always count content via the API, not the landing page. If you say "there are 49 more" based on a brochure and the API returns 2, the user will (rightfully) call you out.
- **Bunny.net segments are `.dts`, not `.ts`** — segments in the media m3u8 are named `video0.dts`, `segment-123.dts`, etc. yt-dlp's HLS demuxer refuses with `is not in allowed_segment_extensions`; ffmpeg's HLS demuxer rejects for the same reason, and `--downloader-args "ffmpeg:-allowed_extensions ALL"` is **not reliably passed through** to the inner ffmpeg invocation. **Use yt-dlp only for `-g` URL extraction, then run manual AES decrypt yourself.** Don't try to make yt-dlp download — wasted hours during the ononno.com session.
- **Bunny.net key host ≠ playlist host** — m3u8 lives on `vz-XXXX.b-cdn.net`, but the `EXT-X-KEY` URI is also rooted at the **same** `b-cdn.net` host (e.g. `https://vz-XXXX.b-cdn.net/{guid}/key/{hash}`). Don't prepend `iframe.mediadelivery.net` to the key URI — it 404s. The key fetch also needs `?token=…&expires=…` appended (the same token from the embed URL); without it you get an HTML login page, not 16 bytes.
- **`yt-dlp -g` is the right way to resolve Bunny URLs** — the `/play/{libId}/{guid}` endpoint returns HTML, not m3u8, when called by `curl`/`requests`. Only yt-dlp's BunnyCdn extractor knows to internally resolve to the `b-cdn.net` media playlist. So: `yt-dlp --cookies X --add-header Referer:Y -g {embed_url}` to get the actual m3u8 URL, then fetch + decrypt yourself.
- **Netscape cookies file MUST have the `# Netscape HTTP Cookie File` header** — yt-dlp refuses cookies files without those 3 header lines (returns `does not look like a Netscape format cookies file`). A plain `domain\tpath\t...\tname\tvalue` file gets rejected silently and the download fails with "video is inaccessible". Always write:
  ```
  # Netscape HTTP Cookie File
  # https://curl.haxx.se/rfc/cookie_spec.html
  # This is a generated file! Do not edit.
  ```
  before any cookie rows. The `secure` column is TRUE/FALSE; `tailmatch` (the `TRUE` after domain) is TRUE only if the domain starts with a dot.
- **3-byte UTF-8 filenames (Bengali, Hindi, etc.) hit ext4's 255-byte path limit** — sanitize aggressively (≤60 chars) for the filesystem-safe output name. Store the full original title in a sidecar `MANIFEST.json` so the user can rename later. The error is `[Errno 36] File name too long` and fires at the `.ts.tmp` write, not the final `.mp4`, which makes it confusing.
- **Klasio's login form has an optional `fingerprint` field** — the form on `/auth/login` has `_token` (from `<meta name="csrf-token">`), `fingerprint` (filled client-side by fingerprintjs v4 from CDN), `email`, `password`. Server-side accepts requests **without** `fingerprint` — fingerprintjs is bot-detection telemetry, not auth-required. Skip it on the first attempt; only fill it if the bare POST returns an error.
- **Always check `/play/{libId}/{guid}` content-type before parsing** — Bunny returns the actual m3u8 only when yt-dlp's exact request signature is sent. A plain `curl` or `requests.get` to `/play/...` returns an HTML wrapper page. Use `Accept: application/vnd.apple.mpegurl,*/*` AND let yt-dlp do the URL resolution — don't try to hit `/play/` directly with your own headers.
- **Probe for ALL content types before declaring a course "done"** — these platforms put videos, notes/PDFs, and sometimes assignments/files in SEPARATE tabs (Synapse: `/videos/{id}/lecture` for video grid, `/notes/{id}/lecture` for PDF grid). After finishing the video download, always check the notes tab too. A common failure mode: downloading 2 videos and declaring the course complete when there are 16 PDFs still on the server. The user will say "there are some pdf/notes too" — that's a signal you should have probed earlier. See `references/synapse-pdfs-and-notes.md` for the full PDF/notes download recipe.

- **Synapse Medical Academy** (`lms.synapsepg.org`) — `player.vidinfra.com` iframe, `kms.vidinfra.com` key server, `jrgtfb2pnx.tenbytecdn.com` CDN, `rumito.tenbyte.io` RUM. AES-128, ~924 kbps 720p H.264 / AAC.

- Other Bangladeshi medical / engineering coaching platforms appear to use the same `vidinfra.com` / `tenbytecdn.com` infrastructure. If the user pastes a new platform URL, check for these hostnames first — if present, this exact recipe applies with no code changes other than the LMS URL and credentials.
- **Klasio (Bunny.net Stream) — e.g. ononno.com, other Laravel + Next.js / Alpine.js course platforms** — player is `iframe.mediadelivery.net/embed/{libraryId}/{guid}?token=…&expires=…` (libraryId is constant per platform, e.g. `421524`). HLS playlist + segments live on `vz-XXXX.b-cdn.net`. AES-128 encryption, but the **segments are named `*.dts` (not `.ts`)** — yt-dlp and ffmpeg HLS demuxers both reject them; only the manual decrypt + remux pipeline works. ### Fingerprinting an unknown platform

When the user pastes a new LMS URL, three signals tell you which recipe applies:

1. **Inspect the lesson page** for `<script src=…>` — look for `iframe.mediadelivery.net`/`b-cdn.net` (Bunny/Klasio) vs `player.vidinfra.com` (Synapse/tenbyte) vs `mux.com`/`vimeo.com` (Mux/Vimeo — usually unencrypted, plain yt-dlp works).
2. **Inspect the iframe URL pattern** — `embed/{libId}/{guid}` is Bunny; `stream/{contentId}/default/{streamId}` is tenbyte.
3. **Check segment extensions in the m3u8** — `.ts` is normal; `.dts` is Bunny's variant and forces the manual pipeline.

## When the course has more than videos: notes, PDFs, files

These LMSes store different content types in different tabs and call different APIs. **After finishing video downloads, always probe for other tabs before declaring the course done.** A chapter with 2 videos may have 16 PDFs sitting on the notes tab.

| Content type | URL tab | Backend |
|---|---|---|
| Videos | `/videos/{chapter_id}/lecture` | HLS stream (this skill's main recipe) |
| Notes / PDFs | `/notes/{chapter_id}/lecture` | Direct file from CDN — no HLS, no encryption |
| Live classes / schedule | `/live/{...}` | (varies) |
| Exams / MCQ banks | `/exams` or per-chapter | (varies) |

The notes/PDF flow is much simpler than the video flow — no HLS, no AES key, no per-segment decryption. The API call is the same `localStorage.sessionId` Bearer-token pattern, but the response is a JSON list of files with a `key` field (S3 path) that downloads directly from the assets CDN.

```bash
# 1. Login via Playwright (same as video flow)
# 2. Capture the Bearer token
sessionId = await page.evaluate("localStorage.getItem('sessionId')")
# 3. Hit the API
curl -H "Authorization: $sessionId" https://api.synapsepg.org/api/lecture/$CHAPTER_ID
# Returns: { "data": { "videoContents": [...], "fileContents": [{"_id", "title", "key": "directory/123.pdf", ...}] } }
# 4. Download each file from https://assets.synapsepg.org/{key}
```

The full reusable script is in `scripts/download_notes.py` — handles login, file enumeration, sanitized filenames, error per-file, and reports total size at the end.

## Delivery to user

Output is typically 500 MB – 2 GB. Discord rejects > 25 MB. Delivery options:
- **Telegram** — supports up to 2 GB via `MEDIA:/path` syntax; user receives as a file in their home channel.
- **SFTP/SCP from server** — `192.168.0.222:/root/...` (Dr. Sagar's usual pattern; fastest on LAN).
- **Remux first** — `ffmpeg -i input.ts -c copy output.mp4` is instant, same size, true MP4 container. Some Android players (older MIUI) refuse `.ts` even with the `.mp4` extension.
